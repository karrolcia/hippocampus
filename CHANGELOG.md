# Changelog

## Unreleased

### Security

- **Patched the August Dependabot batch (5 alerts) — and the only one that could actually be reached was the one labelled "medium".** `hono`'s CORS middleware has a ReDoS in its `Access-Control-Request-Headers` handling, and `cors()` is mounted on `app.use('*')`, which means a preflight reaches it *before* any auth check — an attacker-controlled header on an unauthenticated path, which is about as reachable as it gets. The two "high" alerts were not: `fast-uri` (via the SDK's `ajv`) only validates URI formats in our own static tool schemas behind OAuth, and all three `ip-address` alerts arrive through `express-rate-limit`, which is imported solely by the SDK's `server/auth/handlers/*` and `server/express.js` — modules this server never loads, running as it does on `WebStandardStreamableHTTPServerTransport` with a self-contained `src/auth/oauth.ts`. Patched all five regardless, on the D8 principle that unreachable-today is not a contract. All three resolved in-range, no overrides needed: `hono` `4.12.30 → 4.13.1` (floor bumped to `^4.13.1`, single deduped copy across the tree), `fast-uri` `3.1.4 → 3.1.5`, `ip-address` `10.2.0 → 10.4.0`. `npm audit`: 0. NB: the `fast-uri` alert is a *new* advisory, not a D8 regression — 3.1.4 was the correct patch in July.

- **Cleared all six Dependabot alerts (3 high / 2 moderate / 1 low) in one lockfile sweep.** None were reachable in how this server actually runs — the sharp/libvips CVEs live in image decoding paths a text-embedding server never calls, the adm-zip 4GB-allocation bug sits in onnxruntime's GPU-binary extractor that the Docker build explicitly skips, and the `@hono/node-server` path traversal needs `serveStatic` *and* Windows, neither of which is present — but "unreachable" and "unpatched" make poor roommates. `@hono/node-server` bumped `^1.19.14` → `^2.0.5` (major: drops Node 18, removes the Vercel adapter; `serve()` unchanged), with overrides pinning `sharp ^0.35.0` and `adm-zip ^0.6.0` past their parents' stale ranges; `fast-uri` 3.1.4 and `body-parser` 2.3.0 came along in-range. `engines.node` is now honest about the new floor: `>=20.0.0`. `npm audit`: 0.

- **`HIPPO_AGENT_TOKEN` accepts a comma-separated LIST of agent tokens.** Multiple self-hosted agents (e.g. a laptop + a server) can each hold an independently-revocable token — revoke one by removing its entry and redeploying, without rotating the others. `matchesAgentToken` timing-safe-compares the candidate against each entry and enforces the 32-char floor **per token** (stronger than before, which only checked the whole value). A single token (no comma) behaves unchanged. NB: this is a SERVER-side list — clients (`sync-agents.ts`, the Mac Keychain) still hold a single token; never place the comma-list in a client's `HIPPO_AGENT_TOKEN`.
- **`scripts/sync-agents.ts`** — Phase 1 migration tool for the Agent Continuity Layer spec. Pushes `~/.claude/scheduled-tasks/<id>/SKILL.md` files into Hippocampus as `agent:<id>` entities with `instruction` + `schedule` observations, and pulls them back out for Claude Code compat. `push --dry-run`, `pull --dry-run`, and `list` for inspection without side effects. Auth via `HIPPO_AGENT_TOKEN` or macOS Keychain fallback.
- **`scripts/agents-manifest.json`** — Bootstrap cron/requires data for the 9 existing scheduled tasks, since SKILL.md frontmatter doesn't carry scheduling metadata. After the first push Hippocampus is canonical; the manifest becomes a historical artifact.

### Fixed

- **`merge` no longer strips the classification off everything it merges.** `merge.ts` called `createObservation(entityId, content, source)` — three of the five parameters — so every merged observation was written with `kind -> null` and `importance -> 1.0` regardless of what its sources carried. Same defect that was fixed for `update()`; `merge` never got it, and it is the more destructive of the pair, because merge deletes its sources. The 2026-08-09 curation pass measured the blast radius rather than guessing at it: all 15 compress groups in that digest and all 1,025 compress candidates — the entire change type, not one entity. What that costs is not the text, which survives intact, but the classification the text is retrieved *by*: `skill:*` entities split `kind: "trigger"` from `kind: "content"` and the skill-retrieval protocol reads the trigger to decide whether to load the content at all; `block:*` idea banks split `idea` from `seed`; `course:product-sense` carries an observation documenting its own kind convention, which a merge would have erased while leaving the sentence describing it perfectly intact. Now `kind` and `importance` both carry through, and the multi-kind case is refused rather than resolved — two or more distinct kinds among the sources throw, naming each of them, *before* anything is embedded or deleted, since a merged observation cannot hold two classifications and picking one silently is precisely how a classification dies quietly. A `null` kind is treated as no opinion rather than a third kind, so folding an unclassified stray into a kinded group still works. `importance` takes the maximum of the sources: 1.0 is the schema ceiling, not a neutral value, so the old reset silently *promoted* any group that had been deliberately de-prioritised.

- **`recall`'s `since` filter no longer answers "nothing happened" to every ISO-8601 date.** Observations store `created_at` as SQLite `datetime('now')` — `YYYY-MM-DD HH:MM:SS`, space-separated, in a TEXT column — so `created_at >= ?` is a lexicographic comparison, not a temporal one. ISO's `T` is ASCII 0x54, above both the space (0x20) and every digit, so a `T`-separated bound sorted above every stored row and filtered out the entire table. Measured against the live server, same query and limit with only the spelling varying: `since: "2026-08-25"` returned 37 results, `since: "2026-08-25 10:36:55"` returned 19 with correct time-of-day filtering, and `since: "2026-08-25T10:36:55"` returned **0, with `success: true` and no error** — on the exact format the tool's own schema documented. It failed toward absence, on the one parameter whose whole job is answering "what landed since my last run", so every scheduled sweep that asked got a clean success with nothing in it and concluded nothing had happened. `since` now accepts the date-only, space-separated, `T`-separated, `Z`-suffixed and offset-bearing forms and normalises them to the stored UTC form; offsets are converted rather than stripped, so `2026-08-25T13:36:55+03:00` is `10:36:55`, not `13:36:55`. Anything it cannot parse is now an **error** rather than an empty result — including the well-shaped impossibilities (`2026-13-01`, `2026-02-30`) that would otherwise normalise straight back into a bound matching nothing. Fractional seconds are truncated to the stored second resolution, which on an inclusive lower bound errs toward returning an extra row and never toward hiding one.

- **`recall`'s `spread: true` no longer ignores the `since` bound.** Spreading follows relationships one hop out and reads embeddings directly, so it never passed through either filtered query — and because spread results are merged, re-sorted by score and cut to `limit`, damped out-of-window hits could push the in-window rows out of the answer entirely. On the regression fixture: a bound of 2026-08-25 with `limit: 2` returned two observations from 2020 and none of the rows asked for. That is the same "nothing new happened" outcome as the bug above, in a shape that reads as a healthy result set rather than an empty one. Two inputs that used to work now error, deliberately. An empty-string `since` was treated as *no* bound and returned everything — almost always an unset variable, and a full result set reads as "all of this is new". A truncated bound (`2026`, `2026-08`) is the other case, and it genuinely worked: a lexicographic prefix is a correct lower bound. It errors now because a partial date is far more likely a truncation bug than an intent, and a bound that can't be fully resolved should say so rather than quietly answer.

- **Stored timestamps are read as the UTC they are.** `new Date('2026-08-25 10:36:55')` parses a zone-less string as *local* time (per ES2015+ only date-only forms are UTC; the `T` separator does not change this), and `datetime('now')` writes UTC — so `recall`'s 30-day staleness hint and `consolidate`'s sleep-mode `age_days` bucketing were both shifted by whatever offset the host happened to run at. The production container is UTC, so the live skew is currently zero; that is a property of the deployment, not of the code, and the same database answered differently on a laptop in Helsinki, where the sync script and the whole test suite run.

- **`remember` can no longer silently delete a log entry it mistook for a repeat of itself.** Dedup on write deletes the stored observation when a new one scores >= 0.85 cosine and is longer — fine for a fact being restated with more detail, catastrophic for an append-only log, where two dated entries can clear 0.85 on their shared template alone. Four confirmed losses, the last of which was a 9,197-char knowledge-harvest entry evicting the 6,182-char entry from three weeks earlier on `ops:daily-log:hippocampus`: unrelated content, different windows, over the line purely on the skeleton they share. Two guards now bound the destructive path. (1) **Append-only entities** — names matching a `HIPPO_APPEND_ONLY_PREFIXES` prefix (default `ops:daily-log:`, `ops:session-check`, `synthesis:`) are exempt from dedup entirely, so neither the delete branch *nor* the skip branch can touch them; a skip loses the new entry, which for a log is the same wound in the other direction. (2) **Same-UTC-day scoping** — everywhere else, dedup only ever considers observations created on the same calendar day, so two entries written on different days cannot evict each other no matter how alike they look. This protects log entities nobody remembered to list. Day equality rather than a rolling N-hour window on purpose: a rolling window fails *destructively* at midnight (23:58 and 00:05 are seven minutes apart and two different days' entries), while day equality fails safe — worst case a midnight-straddling retry stores a duplicate, which is what `consolidate` is for. Same-day dedup on ordinary entities is unchanged.

- **`recall` stops telling you your log entries are out of date.** The `stale: true` reconsolidation hint fires on observations older than 30 days when the entity has received newer information since — which, on an active log, is a description of every historical entry it holds. Measured against the live store before the fix: **5 of 5** recalled log observations came back flagged. The suggested remedy for a stale observation is `update`, which is create-new + delete-old, so the highest-frequency read path in the server was inviting the destruction of dated records, constantly, with a 100% false-positive rate on exactly the entities two prior fixes had just finished protecting. Append-only entities are no longer flagged. Everywhere else the hint is unchanged — an old fact on an entity that has moved on really may need refreshing; an old log entry is not out of date, it is the entry for that date.

- **`consolidate` no longer proposes consolidating your logs.** D10 stopped `remember` from evicting dated log entries; it did nothing about the tool whose entire job is to hand back merge candidates. All four modes were affected, and the arithmetic was not close: two consecutive knowledge-harvest entries cluster at 0.948 against a 0.8 default (message: "use merge to consolidate", full content and observation ids attached); `mode: "sleep"` buckets every never-recalled observation older than 30 days as `prune`, which is a description of the entire `ops:daily-log:*` history, since a daily log is recalled by semantic search across entries and essentially never as an individual observation; and `entities` mode scores `ops:daily-log:codesea` against `ops:daily-log:rsl-content` at **0.688** — a whisker under the 0.7 default, so one threshold tweak from proposing that two different projects' logs are the same entity. Now: append-only entities are excluded from every mode, the count comes back as `excluded_append_only` and is named in the message (a filter whose drops are invisible is how the original eviction went unnoticed for months), and an entity-scoped call on a log entity says what happened instead of returning a bare "no observations found" — that shape of reassuring silence is the whole reason this saga has a D10 and a D11. `include_append_only: true` restores the old behaviour for the one real use case: hunting accidental double-writes, which D10 made more likely by removing dedup from these entities entirely.

- **On an append-only entity, `remember` no longer asks you to delete the entry it just saved.** Overlap between dated log entries is reported (that was the point — the old code hid it), but reporting it as *"these observations overlap — consider consolidating"*, with the full stored text of each, was an invitation with the key attached: `near_matches[].content` was byte-identical to the stored observation, which is exactly what `update` matches on, and the `onboard` prompt tells the AI that low novelty plus high overlap means `update` or `merge`. So the server would preserve the 07-31 harvest entry and then hand the model everything it needed to remove it by hand, on every daily-log write. Now: on append-only entities the reported matches are 200-char previews (non-executable by construction — a stray `update` fails safe with "no observation matching the old content"), the message says plainly not to consolidate, and `onboard` step 4 carries an explicit exception for `append_only` responses. Off the log entities nothing changes: full content, same consolidation nudge, because there consolidation is the intended workflow.

- **`replace_kind` now hands back what it deleted.** It reported a count and nothing else, which is a strange asymmetry for the `remember()` path with the *widest* blast radius — it deletes every observation of that kind, not one. Now: `replaced_observations` with the id and full text of each, plus `append_only: true` when the entity is a log namespace, so a caller can see it just bulk-deleted from an append-only entity and can put the entries back. Explicit caller intent is still honoured — `replace_kind` is not blocked on append-only entities, only reported.

- **A `remember` response now admits when it destroyed something.** The old failure mode was worse than the deletion: >= 0.85 matches went to the dedup branch and only 0.5–0.85 matches went to `near_matches`, so at the precise moment a write deleted an observation, `near_matches` came back **empty** — the most reassuring shape available, at the worst possible time. The eviction was announced only in the prose `message` and `replaced_observation`, both easy to drop when parsing a field subset, leaving a before/after observation count as the sole reliable detector. Now every destructive result carries a top-level `replaced: true` alongside `replaced_observation` (full evicted text) and `replaced_observation_id`; `replace_kind` writes report `replaced` + `replaced_count`; non-destructive results say `replaced: false`. Matches held back by a guard are pushed into `near_matches` instead of vanishing, so a >= 0.85 overlap is visible without being acted on, and an append-only write is flagged `append_only: true`.

- **`update` no longer gives observations amnesia about what kind of thing they are.** A memory server whose edit operation forgets metadata is a little too on-the-nose. `update` created the replacement observation with only `content` and `source`, so `kind` reset to `null` and `importance` quietly reverted to 1.0 — edit a `kind:"content"` skill prompt and it came back an unclassified blob, invisible to every kind-filtered recall. Worse, passing `kind` explicitly was silently stripped by Zod (unknown schema key), so the call *looked* like it worked. Now: `kind` and `importance` carry over by default, and `update` accepts an optional `kind` param to set (or re-tag) it. The response includes the resulting `kind` so you can believe your own eyes.
- **`forget` with a `content` argument no longer escalates to deleting the entire entity.** The old schema knew only `entity` and `observation_id`; Zod strips unknown keys rather than rejecting them, so `forget({entity, content})` — a reasonable attempt at "delete this one observation" — arrived as `forget({entity})` and torched the whole entity, observations, embeddings, relationships and all. A scoped delete that silently widens its blast radius is the worst kind of helpful. Two fixes: (1) `content` is now a real parameter — exact-match a single observation on the entity and delete only that; a miss deletes nothing and says so. (2) `forget` is now a strict tool at the param-normalization boundary: any unrecognized argument is rejected loudly (naming the key, never the value) instead of being shrugged off. Bonus: `forget` by `observation_id` now refreshes the entity's `version_hash`, which it had been forgetting to do all along.
- **`context` tool now exposes observation `kind`.** V5 added the field in 2026-02 but `formatObs` dropped it when serializing — so any AI consuming `context` couldn't tell an `instruction` observation from a `schedule` one even when both existed. Surfaced while writing the agent sync tool; fixed at the point it was actually needed. No schema change.

### Changed

- **`onboard` tool now scales with DB size.** Previously it fetched all entities (up to 10,000) and ran `getObservationsByEntity` per entity just to produce a count — an O(N) loop with a DB round-trip per iteration, fine at 20 entities, painful at 500. The prompt also dumped every entity name as a comma-separated list, so a mature instance spent ~2K tokens on the existing-entities block alone, crowding out the actual extraction guidance. Now: single SQL `COUNT(*)` for observations, single SQL `GROUP BY` for namespace distribution, top 30 most-recently-updated entities as concrete examples. The AI sees namespace counts (`project:` (23), `skill:` (15), `pattern:` (1)) plus recent names plus a note to `recall` for exact-name duplicate checks when needed. Output shape is unchanged (`existing_entities` still returned, now truncated to the recent slice).
- **`onboard` prompt now names patterns as a first-class inventory category.** Added "Recurring patterns the user diagnoses across encounters (founder archetypes, sales traps, failure modes)" to the inventory list, `pattern:<name>` to the entity naming convention, `"pattern"` to the type enum, and a worked example. The motivation: pattern recognition only compounds if the patterns themselves are entities — otherwise every similar intro call reconstructs the same diagnosis from scratch. The prompt nudges AIs to capture the archetype alongside the specific instance.
- **`onboard` now branches on DB maturity.** Below 50 observations the prompt is bootstrap mode (full inventory extraction across 9 categories — the right shape for a cold start). At 50+ observations it switches to ongoing mode: an explicit "do not re-extract, capture deltas only" directive, a CAPTURE/DO-NOT-CAPTURE rule pair, near_matches handling (novelty < 0.3 → update or merge; 0.3–0.6 → capture with relationship; > 0.6 → genuine new info), `importance` parameter guidance for identity facts and load-bearing decisions, and delta-shaped examples. Mature instances kept getting the wrong job description from the bootstrap prompt — bulk extraction when the actual need was mid-conversation capture. Both modes share the namespace summary, recent-30 examples, and `pattern:` guidance. Verify step now uses `check_version` (uses the version-hash machinery already in v0.4.1) instead of a vague recall query.

## 0.4.1 — "Hey, it's your server calling" (2026-04-10)

OAuth 2.1 is the right front door when Claude.ai and other MCP clients come knocking. It is a terrible choice when your own nightly agent, running on your own laptop, needs to talk to your own server to put together tomorrow's briefing. The refresh-token dance is a failure mode looking for a place to happen — and when it fails, it fails silently at 9am on a Monday, which is exactly when you needed the briefing.

So there is now a second door. Same building, same locks, different key.

### Added

- **`HIPPO_AGENT_TOKEN` env var.** Optional. If set, `bearerAuth()` accepts it as a valid bearer token in addition to OAuth access tokens. Designed for machine-to-machine scheduled agents running on infrastructure you control. Minimum 32 characters enforced in config schema (`Zod.string().min(32)`) — if you are going to bypass OAuth, at least bring a real token.
- **`auth.test.ts`.** Covers missing header, bogus token, valid agent token, length-gate rejection (different length), same-length-different-content rejection. 5 tests, no DB round-trips in the assertions themselves.

### Changed

- **`bearerAuth()` now tries OAuth access tokens first, then falls back to the agent token.** This ordering is deliberate: existing OAuth clients are completely unaffected (the lookup is the same, the behavior on success is the same). Only tokens that fail the OAuth lookup reach the agent-token check. If neither matches, the response is identical to before.
- **Constant-time comparison for the agent token.** `timingSafeEqual()` was already imported for OAuth. The new `matchesAgentToken()` helper adds a length gate before the compare (buffers must be equal length for `timingSafeEqual` to work at all) and bails out safely on missing config. No length-based side channels.
- **Cleanup interval is now `unref()`'d.** The 10-minute `deleteExpiredOAuthData()` interval used to keep the Node event loop alive, which made the test runner hang after tests finished. It no longer does. This is a test-ergonomics fix, but also a correctness improvement for any script that imports `oauth.ts` and expects to exit cleanly.

### Why this exists

Scheduled agents on the owner's own laptop, hitting the owner's own server, over HTTPS, with a constant-time-compared secret stored in the macOS Keychain — that is a different trust model than a third-party AI assistant asking for access to user data. OAuth 2.1 was designed for the second case and it shows. Trying to force the first case through the same flow means teaching your laptop to handle refresh-token rotation at 3am, and discovering at 9am that it did not.

The new path is scoped at the deployment layer, not in the protocol: if `HIPPO_AGENT_TOKEN` is not set, nothing changes. If it is set, one additional code path exists that grants full read/write on the instance that configured it. Revocation is rotate-the-env-var-and-redeploy. The blast radius is exactly as big as the server that configured the token.

OAuth clients do not need to know this path exists. They will never hit it.

## 0.3.1 — "Room for the big stuff" (2026-02-26)

The 2,000 character limit made sense when every observation was a telegraphic fact. Then you try to store a writing framework, a CLAUDE.md file, a skill template — and you're negotiating with a text box about what to leave out.

Content limit raised to 50,000 characters. The embedding model still only sees the first ~1,500 chars (all-MiniLM-L6-v2 truncates at 256 tokens), so semantic search quality is unchanged for short memories and irrelevant for long ones — artifacts get retrieved by entity name or keyword, not vibes.

### Changed

- **Content limit: 2,000 → 50,000 chars** across all write paths (`remember`, `update`, `merge`). SQLite TEXT columns had no size constraint to begin with. The limit was purely in Zod validation.

### What this enables

- Writing frameworks, skill templates, career histories, CLAUDE.md files
- Any artifact you want available across AI tools without copy-pasting
- Store once in Hippocampus, retrieve from Claude, ChatGPT, Gemini, Cursor, whatever speaks MCP

- **Richer observation kinds.** `remember` and `onboard` now guide AIs to capture reasoning and exploratory thinking, not just telegraphic facts. Two new kinds: `rationale` (why a decision was made, tradeoffs weighed, options rejected) and `exploration` (half-formed ideas, open questions worth preserving). No schema change — `kind` was always free-text. The difference is in the tool descriptions: AIs now know these kinds exist and have examples to follow.

### What doesn't change

- Semantic search still works on the embedding window (~1,500 chars). Long artifacts rank lower in similarity search — by design, not by bug.
- Keyword search, `context` tool, and `export` all work on full stored text regardless of length. Always did.
- SQLite schema untouched. Existing databases need no migration.


## 0.3.0 — "Did anything change while I was gone?" (2026-02-25)

You told Claude about your project stack on Monday. On Wednesday you switched to Gemini. Gemini has the same Hippocampus connected, pulls your context — but is it still Monday's context? Maybe you updated three things since then. Maybe you didn't. Gemini has no way to know without re-fetching everything, every time, forever.

This release gives every entity a version fingerprint. Now an AI can ask "has this changed?" and get a yes/no answer in one lightweight call. No re-reading observations, no embedding computation. Just a hash check.

Also: onboarding is no longer "figure it out from the tool description." There's a proper onboard tool now that tells the AI exactly what to extract and how to store it.

### Added

- **Entity versioning** (Schema V6). Every entity gets a `version_hash` — SHA-256 of all its observation content, sorted by ID — and a `version_at` timestamp. The hash recomputes automatically on every mutation. Deterministic: same observations, same hash, every time. Existing entities start with NULL and pick up their hash on next write. Nothing breaks.

- **`check_version` tool**. The "did anything change?" tool. AI sends an entity name and a hash it cached last time. Gets back `is_current: true` (relax, nothing changed) or `is_current: false` (time to re-fetch). Works without a cached hash too — just returns current version info. Zero embedding computation. Pure metadata. Fast.

- **`onboard` tool**. First-session extraction, guided. Instead of hoping the AI figures out what to `remember` from tool descriptions alone, `onboard` returns a structured prompt: here's what to look for (identity, projects, preferences, skills), here's what's already stored (don't duplicate it), here's the format (telegraphic, one fact per call). The tool itself stores nothing — it hands the AI a checklist and gets out of the way. Optional `source` param so it can say "you're running in ChatGPT" if that helps.

- **`version_hash` everywhere it matters**. All mutation tools (`remember`, `update`, `merge`, `merge_entities`) return the hash after writing, so AIs can cache it immediately. All `recall` formats carry it — `full` gets the field per memory, `compact` gets `[v:8chars]` in the header, `wire` and `index` get `|v:8chars` inline. `context` includes it on the main entity. If an AI touches a tool that reads or writes entities, version info is right there. No second call needed.

- **Smarter onboarding guidance**. The `hippocampus://context` sparse-state text (< 5 observations) now points to `onboard` instead of just saying "use remember." Because "use remember" is technically correct and practically useless when you're staring at an empty knowledge graph.

### Design notes

**Why entity-level, not observation-level.** We considered `supersedes`/`superseded_by` on observations — proper audit trail, very clean. But it requires soft-delete, and soft-delete means every query path in the system (semantic search, keyword search, consolidate, export, context, spreading activation) needs supersession filters. That's a lot of surface area for a feature whose actual job is answering "did this change?" Entity-level hashing answers that question without touching the deletion model. Also plays nicely with `PRAGMA secure_delete = ON` — when you forget something, it's gone, not marked invisible.

**Onboard returns instructions, not actions.** Every AI platform has different context available — conversation history, system prompts, uploaded files. Hippocampus doesn't know what the AI knows. The AI does. So `onboard` hands it a structured extraction prompt and lets it do what it's good at: reading its own context and calling `remember`.

## 0.2.0 — Memory Lifecycle (2026-02-24)

Hippocampus now manages the full memory lifecycle: encode, sleep, reconsolidate. Three failure modes that accumulate over time — aggregate redundancy invisible to pairwise comparison, dead-weight observations never recalled, and stale facts actively served despite newer information — are now detectable and actionable.

### Added

- **Subspace novelty scoring** on `remember`. Returns `novelty` (0-1) via SVD projection onto the subspace spanned by existing observations. Catches aggregate redundancy that pairwise cosine similarity misses — five observations with moderate individual overlap can collectively explain a new one entirely. Warns when novelty < 0.1.

- **Sleep mode** (`consolidate mode: "sleep"`). Batch lifecycle analysis inspired by hippocampal memory consolidation during sleep. Uses SVD leverage scores combined with temporal signals to classify old observations into three categories:
  - **Compress**: redundant + old + recalled. Merge candidates — information captured elsewhere, safe to consolidate.
  - **Prune**: never recalled + old. Delete candidates — synaptic pruning for observations that never proved useful.
  - **Refresh**: actively used + unique + old. Reconsolidation candidates — the AI keeps serving these, but newer information exists.

  Returns `information_rank` and `redundancy_ratio` per entity for structural diagnosis ("20 observations but only 5 dimensions of information — 75% redundant").

- **Reconsolidation hints** on `recall`. Flags `stale: true` on observations older than 30 days when the entity has received newer information since. Lightweight — date comparison only, no embedding computation. The AI can act on stale flags with the existing `update` tool.

- **`age_days` parameter** on `consolidate` (sleep mode). Minimum age in days for an observation to be a candidate (default 30, range 1-365).

### Dependencies

- Added `ml-matrix` (~50KB, pure JS, zero native dependencies) for SVD computation.

### Design notes

Hippocampus does the math, the AI does the language. Sleep mode returns classified observations — the AI acts on them using existing tools (`merge` for compress, `forget` for prune, `update` for refresh). No new action tools needed.
