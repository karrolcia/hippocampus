### D18 · 2026-08-28 · `merge` carries `kind` and `importance` through, and REFUSES a multi-kind group rather than picking a winner
**Why:** `merge.ts:45` passed three of `createObservation`'s five parameters, so every merged observation was stamped `kind -> null`, `importance -> 1.0` no matter what its sources held — the same defect fixed for `update()`, never applied to the tool that *deletes* its sources. Found by the 2026-08-09 dreaming pass, which is the part worth recording: the curation pass measured the blast radius (all 15 compress groups in that digest, all 1,025 compress candidates) and put the two 2026-07-22 compress proposals on hold rather than proposing a merge that would have executed the bug. The damage is invisible at the point of failure, which is this codebase's recurring shape — the merged *text* is correct and complete; only the classification it is retrieved by is gone, and `skill:*` trigger/content, `block:*` idea/seed and `course:product-sense`'s own kind-convention observation are all retrieved by it.
**Instead of:** *majority kind wins* (rejected by Karolina at the decision point: a 3-summaries-vs-2-conventions group silently loses the conventions' classification, which is the same silent-loss family as the D10 dedup eviction — and this path deletes the sources, so there is nothing to recover from); *kind stays null by design* (the dreaming pass's own counter-assumption, that a merged observation is a new synthesis which should not inherit — a coherent reading, rejected because it makes the curated tier unmergeable in practice rather than by rule, and leaves `importance` reset with no argument at all); *carry the kind but warn* (not seriously weighed — a warning on a path that has already deleted the sources is a notification, not a guard).
**Design choices inside the fix, both arguable:** `null` is treated as *no opinion* rather than a third kind, so `[null, "trigger"]` merges and carries `"trigger"` — the hazard being closed is losing a classification, not gaining one, and rejecting this case would block the ordinary cleanup of folding an unclassified stray into a kinded group. `importance` takes the **max** of the sources rather than the min or the first: the merged observation holds all of the sources' content, and 1.0 is the schema ceiling rather than a neutral value, so the old reset silently *promoted* any group that had been deliberately de-prioritised.
**Failure direction:** loud and non-destructive. The kind check runs after the entity validation and *before* `generateEmbedding`, `createObservation` and the delete loop, so a refused merge costs an embedding call it never makes and leaves every source observation byte-identical. The create/delete half of that ordering is pinned by the non-destructive test; the before-embedding half is verified by reading `merge.ts`, not by a test.
**Positive control:** three mutants, each caught. (1) The original three-argument call restored — **3 of 6** fail (the two reject tests run entirely upstream of `createObservation`, and the all-null test asserts the very `null` the mutant produces, so those three are insensitive to it by design). (2) Carry-through kept, the multi-kind guard disabled — **2 of 6** fail, the two reject cases. (3) The guard kept but moved *after* the delete loop, with a first-source-kind fallback — **1 of 6** fails, and it is the non-destructive test, which is the one that had to have teeth. Suite 305 after the rebase onto `origin/main` and the review round — eight of them new (six merge, two remember) — all green; `tsc --noEmit` clean.
**Review round (separate agent, Opus, 2026-09-02) — REQUEST-CHANGES, all fixed in-branch:** (1) the call-site sweep this entry originally claimed was wrong: `remember.ts`'s dedup-replace branch — a delete path — wrote the *caller's* metadata over the deleted row's, empirically turning a `skill:*` `trigger`/0.3 into `null`/1.0 (reachable: `skill:` is not append-only). Fixed to inherit the deleted observation's `kind` and `importance` unless the caller sets them; two regression tests. (2) `MergeResult` now discloses the surviving `kind` and `importance`, as `update()`'s does — the sources are deleted, so it is the only thing to check against. (3) `kind` gains `.min(1)` at the zod boundary on `remember` and on `recall`'s kind filter (`update` already had it on main); on `remember` and `update` the post-zod control-char sanitiser now yields `undefined` rather than `""`, so a control-char-only kind can neither be stored nor clear a carried one; and the merge guard treats `""` as no opinion. **Undisclosed-then-disclosed (pass 2):** the `recall` change is a read-path contract change — `kind: ""` used to mean *no filter* and returned everything, it is now a validation error, on the D13/D16 principle that an empty string is an unset variable and a full result set reads as "all of this matched". (4) A null `importance` row (column has no NOT NULL) no longer reads as 0 in the max. (5) The ROADMAP's `onboard.ts` collision check, recorded: no collision — max-carry-through is right at any ceiling — but `onboard.ts` still tells callers to pass 1.5–2.0 against a zod cap of 1, and if that cap is ever raised the "1.0 is the ceiling" prose here and in `merge.ts` goes stale. (6) `consolidate`'s compress clusters are kind-blind, so a cross-kind proposal now hard-fails at apply instead of silently damaging — strictly better, still a follow-up (ROADMAP). Authored 2026-08-28 in a session barred from spawning agents; rebased onto `origin/main` and renumbered from D16 (D16/D17 landed first) on branch `claude/merge-kind-carryover`.
**Checked and clean (corrected by the review round):** all five `createObservation` call sites swept — `remember`'s fresh insert and its explicit `replace_kind` overwrite are correct, its dedup-replace branch was NOT (fixed above), `update` was fixed earlier, `merge` is this entry. `merge_entities` is clean **by construction** rather than by luck: it never recreates an observation, it reassigns one (`moveObservationsToEntity` → `UPDATE observations SET entity_id = ?`), so every column including `kind` and `importance` survives — worth stating, since it deletes its source *entities* afterwards and would have been the more expensive sibling. The refusal reaches a client as an error, not just a thrown `Error` in a unit test: the `merge` handler's catch returns `isError: true` with `error.message`, so the conflicting kinds are named in the client-visible text.
**Status:** active.
**Where:** `src/mcp/tools/merge.ts` (kind/importance carry-through, the multi-kind refusal, the disclosed result), `src/mcp/tools/remember.ts` (dedup-replace inherits the deleted row's metadata), `src/mcp/server.ts` (the `merge` tool description states the refusal — a client-contract change; `kind` non-empty on `remember`/`recall`, sanitised-to-undefined on `remember`/`update`, sanitised-and-rejected-if-empty on `recall`), `src/mcp/tools/recall.ts` + `src/mcp/tools/remember.ts` (direct-caller schemas: kind `.min(1)`), `tests/merge-kind-carryover.test.ts` (new, 8 cases), `CHANGELOG.md` Unreleased -> Fixed, `ROADMAP.md` (the item this closes; the compress-kind-blind follow-up; the "Later" contradiction-detection line was also rewritten in this branch — `b42953d`).

### D17 · 2026-09-02 · `sync-agents` fails closed on an in-band tool error, and `pull` refuses a degraded index while `list` only warns
**Why:** D16 made `recall` disclose a degraded search; the repo's own consumer of `recall` then ignored the disclosure, which is how an intent leaks one layer out and stops being true. Two defects, both the same shape as D16 itself — a success signal that is not measuring success. **The larger one was not the degraded flag at all.** An MCP tool failure is *in-band*: HTTP 200, a normal `content` array, and `isError: true` beside it. `HippoClient.call()` never read that flag, so the error TEXT fell through to `JSON.parse`, failed to parse, and was returned as a plain string — and `cmdPush` wraps its calls in try/catch and counts `ok++` on no-throw, so a `remember` the server REJECTED printed `✓ agent:foo`, reported `Pushed 5/5 agents`, and exited 0 having written nothing. That is the exact failure the global notes already record for `claude -p --output-format json` (in-band error, exit code 0, retry logic never fires), rediscovered in this repo's own client. On the read side the same gap surfaced differently: `pull` got a string where it expected an object and died on `undefined.matchAll`, loud but with the cause discarded, and a failed `context` for one agent was reported as `no 'instruction' observation, skipping` — a false explanation for a call that never succeeded. Second defect: a degraded index is a silently shorter agent list, and every count printed afterwards is measured against it, so `Materialized 3/3` is a true statement about a wrong 3.
**The `pull`/`list` split is the decision.** `list` warns and prints; `pull` refuses unless `--allow-degraded`. The line is not read-vs-write, it is whether a labelled subset still answers the question asked. `list` answers "what is in Hippocampus" — a subset with a banner over it is an honest, useful answer. `pull`'s whole promise is that disk ends up matching Hippocampus, and a subset cannot keep that promise *silently*: the agents missing from it are not reported missing, they are simply absent, and nothing on disk or in the output says so. Same split as D16 one layer up — disclose when there is something honest to return, refuse when the operation would quietly come to mean something else.
**Instead of:** warning on `pull` and continuing (rejected: the warning scrolls past in a launchd log and the disk state that outlives it carries no trace, which is the durability asymmetry that makes this different from `list`); refusing on both (rejected: it makes `list` useless in exactly the situation where you most want to look at what the server can still see); treating an absent `degraded` field as degraded (rejected: an older server does not send the field, and this script must keep working against a server it did not deploy. Note this is the *opposite* of D16's server-side rule that absence must not be the all-clear — deliberately: there the field is guaranteed present because the same commit writes it, here it is not, and a missing-field-means-broken client would fail against every server predating D16).
**Made testable, deliberately:** nothing in the script was exported and `main()` ran at import, so neither fix could be regression-tested. It now carries a main-module gate and exports `HippoClient`, `describeDegradation` and `cmdPull` (the last one taking an injectable client). A fix on a write path that reports its own success is precisely the kind that must not rely on nobody breaking it — D13's second review round made the same point about three fixes that shipped with no test between them.
**Review round, folded in:** three findings, and the first is the one that matters — **the `pull` refusal was unpinned**. The reviewer deleted the whole `if (degradation && !allowDegraded) throw` block and the suite stayed green: `describeDegradation` was covered, the branch that acts on it was not. Covering the predicate is not covering the guard, which is this repo's own note on positive controls arriving in a new costume — and it made the paragraph above an overclaim about half its scope, now corrected. `cmdPull` takes an injectable client so the refusal is asserted directly, with two controls (the flag lets it proceed; a healthy index is never refused) so an unconditional throw could not pass in its place. Deleting the guard now fails a test. Second: **the main-module gate silently disabled the entire CLI behind a symlinked path** — Node resolves symlinks for `import.meta.url` but not for `process.argv[1]`, so the two disagree and `isMain` reads false, producing exit 0 with no output. Reproduced via macOS `/tmp` → `/private/tmp`. It is copied byte-for-byte from `src/index.ts`, where a silent no-op is caught in seconds because nothing starts listening; on a sync CLI it is indistinguishable from "nothing to sync", which is the exact failure this entry exists to remove — so this file deliberately diverges from the pattern it copied and compares realpaths on both sides. Third, pre-existing but inside the rewritten block: an agent skipped for a missing `instruction` observation bypassed both counters, so `pull` printed `Materialized 0/1 agents to disk` and exited **0**. Skips are counted, disclosed in the summary and exit non-zero: the caller asked for that agent on disk and did not get it.
**Status:** active.
**Where:** `scripts/sync-agents.ts` (the `isError` check in `call()`, the `pull` refusal + `--allow-degraded`, the `list` banner, per-agent error isolation in the `pull` loop mirroring `cmdPush`, and the main-module gate), `CLAUDE.md` (gotcha), `tests/sync-agents-errors.test.ts` (11 cases). Measured: **2 of 11** fail against the pre-fix `call()` — the two asserting an in-band error rejects — and **1 of 11** fails when the `pull` refusal is deleted, which is the check that was missing before the review. The remaining cases are negative controls (a healthy response still parses, a non-JSON success still falls through to plain text, a healthy index is never refused, `--allow-degraded` still proceeds) plus the `describeDegradation` branches. Full suite 286 → 297.

### D16 · 2026-08-26 · `recall` discloses a failed semantic leg on every response, and refuses to answer at all when the degraded answer would be empty
**Why:** `recall()` called `semanticSearch(query, opts).catch(() => [])`. Semantic search is the **primary** leg and keyword LIKE is the fallback, so any embedding failure — model load, OOM, a corrupt vector, transformers.js throwing — was swallowed and the function carried on with the weaker half of the search. The caller got `success: true` and a smaller result set with nothing anywhere to say the primary leg never ran, which makes a degraded answer indistinguishable from a complete one. At the limit it produced `success: true, count: 0`, byte-for-byte the answer for "the memory holds nothing about this". This is D13's failure family in D13's own function, one line over: quiet, in the direction of fewer results, on the read path every scheduled sweep and every briefing calls. The asymmetry inside the function was the tell — the `spread: true` branch calls `generateEmbedding` with no catch, so the identical failure was fatal there and invisible here, and nothing in the code said which was intended. The rest of the server had already voted: `remember`, `update`, `merge` and `consolidate` all call `generateEmbedding` uncaught. An embedder failure was fatal to every operation in the server **except** the two that could use it to look complete.
**Instead of:** deleting the catch so it throws like the spread branch (rejected: it is the loudest option and the one this repo's instincts pull toward, but it over-corrects. The callers that benefit from the fallback are read-only — briefings, sweeps — and they still get their keyword hits while the embedder is down. Killing that outright buys nothing the flag does not already buy, and recall is the busiest read path in the server); keeping the fallback and flagging it, with no error case (rejected: the flag rescues every cell but one. `success: true, count: 0, degraded: true` is still an empty result set, and this log has four consecutive entries of evidence that a quiet empty gets believed. Applying D10's second-order test — when you replace a bad behaviour with a report, ask what the report authorises — a degraded zero authorises nothing at all, so the only correct caller reaction is to treat it as an error, which is an argument for encoding it as one); logging server-side only (rejected as the whole fix: the app logs almost nothing per-request and request diagnostics live in Caddy's journal, so a log line reaches the operator and never reaches the caller, who is the one drawing the wrong conclusion. Kept as a component, not as the answer); unifying by making the spread branch degrade too (rejected: see below).
**The asymmetry is the decision, not an oversight.** The shared rule is that an embedding failure is always **disclosed**; what differs between the branches is what can honestly be returned instead. Without a query vector there is no dampened relationship scoring at all, so keyword-only results are not a degraded spread — they are a different operation quietly substituted for the one explicitly asked for, i.e. `spread: true` silently becoming `spread: false`. That is this entry's own failure wearing the fix's clothes. Non-spread has a real partial answer and returns it flagged; spread has none and throws. Both branches now carry the reasoning in a comment, because the next reader will otherwise find the same puzzle that started this.
**Failure direction:** degrade visibly when there is something honest to return, throw when there is not. `degraded: boolean` is on **every** recall response and `false` on the healthy path, for the same reason `remember` carries `replaced: false` (D10): a field that appears only when something went wrong cannot be told apart from an older server that never had the field, so absence must not be the all-clear. `degraded_reason` carries the error class and message, capped at 300 chars and never interpolating the query — the same string goes to the server log, and the log is the side that must not carry it. The three text formats additionally get a `DEGRADED` line prepended **inside** `text`, added only when degraded so healthy output is byte-identical: `compact`, `wire` and `index` exist to be read as text, and a disclosure sitting in a sibling JSON field the caller never opens is the same miss the field was added to close.
**Same fix, one tool over — `context`:** `context.ts` had the identical `.catch(() => [])` on its semantic leg. It is not the same case and does not get the same treatment. There the semantic search is the last leg of exact → LIKE → semantic, so when it fails there is never a partial answer to return: the only other outcome is `success: false, "No entity found for topic X"`, which is a false claim about the memory when the leg that would have found it never ran. No recoverable answer, so the catch is simply removed. Fixed here rather than filed, because leaving one of two identical swallows is precisely how D13's spread gap happened.
**Deliberate behaviour change:** a `recall` whose semantic leg fails **and** whose keyword leg matches nothing now throws and surfaces as `isError`, where it previously returned `success: true, count: 0`. This is a contract change on the busiest read path in the server and is the reason this needed its own decision rather than riding along with D13. A caller that treats any error as fatal will now fail where it used to continue — with a wrong answer it could not detect, which is the trade being made. `context` on a topic miss changes the same way: an unresolvable topic throws instead of reporting that no entity exists.
**Checked and clean:** four `.catch(...)` sites in `src` were audited, not just the reported one. `recall.ts` and `context.ts` are fixed; `index.ts`'s `backfillEmbeddings().catch()` is a deliberate boot-time log on a background task that must not take the process down, and `session-registry.ts`'s is transport cleanup with no caller to mislead. No other read path swallows an embedding failure. Recorded because "we looked" is the part that goes missing from a fix.
**Review round, folded in:** the separate-agent pass found no high-severity defect and confirmed all eight entry criteria, including the two things most worth having checked independently — that a degraded response does not *authorise* a loss (it still carries `stale` hints, which invite `update`, but `update` and `merge` both call `generateEmbedding` before any `deleteObservation`, so every destructive follow-up a degraded recall could invite throws ahead of the delete while the embedder is down), and that a corrupt-vector error cannot leak content (a truncated blob yields `RangeError: Invalid typed array length: 384`; the transformers dist has no error template on the feature-extraction path that interpolates input). Two low findings closed. The first is the one worth recording: `formatIndex` returned a literal `degraded: false`, and although the call site's spread always overrode it, the pre-fix shape was a bare `return formatIndex(limited)` — precisely what a later simplification restores, at which point `format: 'index'` reports healthy on a degraded call, silently, in the format that had already lost the flag once. It now returns `Omit<RecallIndexResult, keyof DegradationFlags>`, so the formatter cannot name the flag at all and the call site is the only source. A plausible-looking default that reads as an all-clear is this repo's recurring shape; the fix is to make it unsayable rather than to say it correctly. Second: the tool description stated the degraded contract but not the spread asymmetry, leaving a model that hit the spread error with no description-level route to the recovery that works — it now says to retry with `spread: false`.
**Merged with D15, and the two guards say different things:** D15 landed on the same expression while this was in review, wrapping the semantic leg in a catch that rethrows a `since` contract violation instead of degrading. Both survive, rethrow first, and the distinction is worth naming because it is what stops `degraded` from becoming a shrug: a bad bound is a defect in the caller's **question**, and answering a malformed question with a flagged partial answer is the silent-empty failure D15's assert exists to prevent, reintroduced by the error handling wrapped around it. An embedder failure is a defect in the server's **machinery**, where a keyword-only answer is honest as long as it says so. Order is load-bearing in the other direction too: because the contract error is rethrown before anything sets `degradedReason`, everything the flag reports is an embedding-side failure, which is exactly what it claims to mean. Renumbered from D14 at merge — two siblings landed first, and landed entries do not move.
**Status:** active.
**Where:** `src/mcp/tools/recall.ts` (the flag, the empty-degraded throw placed ahead of every side effect, and the reasoning on both branches), `src/mcp/tools/context.ts`, `src/mcp/server.ts` (the tool description — D13's lesson is that the description string is what every client's model actually reads, so the degraded contract has to be stated there or it does not exist), `CLAUDE.md` (Key Design Decisions), `tests/recall-degraded.test.ts` (14 cases, one of them the D15 interaction: with the embedder down AND a malformed `since`, the error names the bound, not the embedder — `recall`'s own rethrow stays unreachable through the public API for the reason D15 records, so what is pinned is the reachable half) + one healthy-path case in `tests/semantic-efficiency.test.ts`. Measured rather than assumed: **9 of 13** fail against the pre-fix `recall.ts`/`context.ts`; the 4 that pass are the two positive controls and the two behaviours this entry deliberately leaves unchanged. The failure is forced the way it actually happens — `env.allowRemoteModels = false` plus a nonexistent `localModelPath`, so the real model load fails offline and deterministically — rather than by stubbing the module, and a `poison took effect` control asserts `generateEmbedding` rejects before anything else is asserted, since every other test in the file would also pass against a working embedder.
### D15 · 2026-08-26 · The pre-normalized `since` contract is asserted at both DB search functions, not documented on them
**Why:** D13 left the two functions that actually run the lexicographic SQL — `searchObservations` and `semanticSearchWithVector` — taking `since` as a raw string, with "must arrive already normalized" held by a jsdoc comment on each `SearchOptions` interface. Today's exposure is nil: `recall()` is the only caller that passes a bound and it normalises. The problem is the *next* caller. A jsdoc is a guarantee that holds exactly as long as someone reads it, in a codebase whose last four entries (D10, D11, D12, D13) are all about paths that fail quietly toward "there is nothing here" — the one failure a memory server cannot afford. Worse, the pinning test D13 added was actively load-bearing in the wrong direction: `tests/recall-since.test.ts` asserted that an un-normalized `T` bound **returns zero rows** at that layer, so a future second caller forwarding a caller-supplied date would have reintroduced D13's exact bug with the suite green and a test certifying the silent zero as intended behaviour. A characterization test for a defect is documentation until someone mistakes it for a specification. `assertStoredSinceBound` in `src/db/timestamps.ts` (one exported helper, so the `STORED_FORM` regex and the message stay in one place) is called at the top of both functions; the pinning test now asserts a throw, and the semantic leg — which never had one — got the same coverage.
**Instead of:** leaving the jsdoc-only contract (rejected: this is the reversal being weighed, and the argument for it is that the exposure is hypothetical — but the cost of the assert is three lines and a provably-unreachable throw, while the cost of being wrong is a silent empty result set on the one parameter that answers "what landed since my last run"); normalising inside the two functions rather than asserting (rejected for D13's original reason, which still holds: a converter there would absorb the caller's bug and split the single normalization point in two — the assert refuses and does nothing else); making the SQL temporal with `datetime(o.created_at) >= datetime(?)` (rejected in D13 and still rejected: it discards `idx_observations_created` on every filtered recall, where a shape check on the *bound* costs nothing and touches no query plan); exporting the raw `STORED_FORM` regex for both call sites to test against (rejected: it duplicates the throw message at two sites, and the message is the part a future debugger reads); **a branded type** — `normalizeSinceBound` returning `string & { readonly __stored: unique symbol }` and both `SearchOptions.since` requiring it (this is the stronger reading of "structural": the violation becomes a *compile-time* error, caught in the editor before the code ever runs, and the first draft of this entry failed to weigh it at all — the round-2 reviewer named the omission). Rejected, but narrowly and on grounds worth stating: a brand is erased at runtime, so it does not cover the untyped callers in `scripts/`, it is defeated silently by any `as string`, and it cannot produce the diagnostic message — which is the artefact that actually rescues the next debugger, since this whole family of bugs is invisible at the point of failure. A brand would compose *with* the assert rather than replace it; if `since` ever gains a second normalized sibling, revisit.
**Reversal, and why the earlier call was made:** D13's entry gate explicitly decided *no throw paths in the DB layer* — "they have no error channel, so a bad bound could only be swallowed there." That reasoning is wrong on inspection, and naming why is the point of this entry: these are synchronous functions, a throw propagates to the same MCP `isError` surface `normalizeSinceBound`'s own throw already uses, and it is the codebase's established way to refuse a bad bound. What the layer actually lacks is a way to *recover* from one — and an assert does not try to. So this narrows one D13 sub-decision rather than reversing D13: the normalise-once-in-`recall()` architecture stands untouched; only the enforcement of its precondition moves from documentary to structural. The distinction that unlocked it is normalise-vs-assert, which the original framing collapsed into one question.
**Failure direction:** loud, and unreachable in production by construction. `normalizeSinceBound`'s output always matches `STORED_FORM` — the two zone-less branches validate by round-trip through `toStoredForm`, the offset branch shape-checks explicitly — so the assert cannot fire on any path that goes through it. A test pins that pairing directly (normalisation output fed back through the assert), because a normaliser that could emit a shape its own assert rejects would throw on every bounded recall in production. `since: undefined` passes as "no bound"; `since: ""` throws, matching D13's stance on the same input one layer up — under `if (options.since)` an empty bound silently drops the filter and returns *everything*, which a caller reads as "everything is new".
**Positive control:** the five original throw-assertions were re-run against a stubbed no-op assert and **5 of 5 fail**; the two `doesNotThrow` cases pass under the stub, correctly — they guard the opposite direction, that the assert never fires on a valid bound. Each review-round fix got its own control: reverting the assert to shape-only fails the unreal-bound case, and dropping the `SINCE_CONTRACT_ERROR` marker fails two. Recorded because "X is no longer possible" proves nothing without showing the fixture would otherwise have fired.
**Checked and clean:** `searchObservations` and `semanticSearchWithVector` are the only two functions that compare a caller-supplied bound against a stored timestamp **lexicographically**; `semanticSearch` reaches the guard transitively, `context` passes no bound, `consolidate` takes `age_days: number`, `export` has no date filter. `recall`'s spread path compares the same bound too, but as *instants* via `parseStoredTimestamp` — immune to the `T` bug by construction, which is why it needs no assert. One existing test changed (the flipped pinning test) — every other `since` call site in the suite already pre-normalised, which is why the rest of the suite stayed green.
**Review round, folded in:** no high-severity findings; the reviewer reproduced the positive control independently and fuzzed 3,616 inputs of its own choosing through `normalizeSinceBound` for a shape the assert would reject, finding none (that input set was not reproducible by the next round — the figure is the reviewer's, and the independently verified numbers are in the second round below). Three fixes worth the round. (1) **The assert was shape-only, and the shape is a proxy for the precondition rather than the precondition itself** — `2026-02-30 00:00:00` matched `STORED_FORM`, so it passed, and lexicographically that bound excludes every late-February row while admitting March: a silently *wrong* window rather than an empty one, the same defect in better clothes. It is also precisely what string surgery produces (JS months are zero-based, day arithmetic overruns), i.e. what a caller who skipped the normaliser would most plausibly build. Now checks the instant too, via an `isRealStoredInstant` predicate factored out of the existing `assertRealInstant` so the round-trip logic stays single-sourced. (2) **The new throw was swallowable — in theory only, and this one is hardening rather than a defect closed.** `recall()` degrades a failed semantic leg to `[]` via `.catch(() => [])`, correct for a model-load or embedding failure and wrong for a contract violation, which would have surfaced as a thin result set reading like a ranking quirk. The error now carries `name = SINCE_CONTRACT_ERROR` and that catch rethrows it. Booked honestly: `recall()` normalises before either leg sees the bound, so the swallow was never reachable, and round 2 confirmed by control that deleting the rethrow leaves the suite green — it cannot be tested from outside without stubbing the normaliser. It is four lines of defence against a future refactor, and it is scope the brief did not ask for. Kept, because a fail-loud guarantee that holds only because some *other* call happens to run first is the shape this whole series is about — but recorded as beyond-the-brief hardening, not as a caught bug, because a review round that inflates its own findings is the next thing to go wrong. ### D3 · 2026-07-17 · Bound MCP session lifetime with a server-side idle sweep (OOM fix)
**Why:** the `/mcp` handler kept one fully-wired `McpServer` per session in a Map that only evicted on an explicit client `DELETE` (the SDK transport's `onsessionclosed` fires nowhere else — verified in `webStandardStreamableHttp.js`). Claude.ai and most HTTP MCP clients reconnect with a fresh session and never DELETE, so sessions accumulated across ~7 weeks of uptime until the process OOM'd at ~1.9 GB *live* heap — while the DB was only 5.8 MB, which is exactly what made it look like a query/data problem and wasn't. Fix: `src/mcp/session-registry.ts` — per-session last-seen, a 30-min idle sweep evicts inactive sessions (unref'd timer), a 1000-session LRU backstop, and an in-flight guard so a busy session is never cut mid-request; `/health` now reports the live session count for verification.
**Instead of:** raising `--max-old-space-size` / adding a container `mem_limit` (rejected — a band-aid that only delays the same OOM as sessions keep accumulating; the leak is unbounded, so any ceiling is eventually hit); relying on clients to send DELETE (not in our control). Instrument-first (per-call logging + heap snapshot) was considered but the static + SDK evidence and the 7-week-uptime→OOM profile were conclusive, so the fix shipped directly.
**Status:** active.
**Where:** commit `17147ac` (`fix/mcp-session-leak` → main), deployed + verified 2026-07-17 (`/health` `sessions` gauge live, container `RestartCount=0`); failure-mode note in CLAUDE.md → Known Gotchas.

### D2 · 2026-07-16 · Adopt the production-memory direction: append-safe writes + out-of-band curation
**Why:** the 2026-07-16 context-engineering talk (memory/versioning/dreaming at scale) names the inversion behind our own recorded failures: Hippo puts judgment in the write path (dedup-on-write deciding to replace content — which silently destroyed a dated log entry) while curation stays manual, where the production pattern is the opposite — write path dumb and deterministic (append-safe, hash-preconditioned, permission-guarded), judgment scheduled out-of-band with human-reviewed proposals. The talk also *validates* the core bet: its portability principle (files with a standalone API on top) is Hippo's thesis — the "file systems are state of the art" claim only holds when agents share a filesystem, which cross-surface agents don't. Concretely adopted: the four ROADMAP items (append-safe writes, `precondition_hash`, protected entities, mutation audit log).
**Instead of:** replacing Hippo with file-system memory (rejected — no shared filesystem across Claude.ai / ChatGPT / launchd agents; the file memory remains the in-repo arm, Hippo the cross-surface arm); observation-level version history (re-rejected — conflicts with `secure_delete`, see CLAUDE.md's entity-versioning decision; the audit log records who/when/which-entity, never content).
**Status:** active.
**Where:** `ROADMAP.md` → "Next — production-memory block"; ops-side dreaming pass in `~/chief-of-staff/ROADMAP.md` #19; AppKeep shared instance in AppKeep `DECISIONS_LOG.md` D.110.
