### D6 · 2026-07-21 · `HIPPO_AGENT_TOKEN` accepts a comma-separated list (per-agent revocable tokens)
**Why:** the estate now has two self-hosted machine-to-machine agents — Karolina's Mac and the ops-backbone loops box — sharing one static agent token. Sharing means revoking one (e.g. the internet-facing box, if compromised) forces rotating the other. So `matchesAgentToken` now splits `config.agentToken` on `,`, trims each entry, enforces the 32-char floor **per token** (previously only the whole value was floor-checked), and timing-safe-compares the candidate against each (returns on first match; a non-match still iterates every entry, so failed guesses are position-independent in time). Each agent holds its own token; revoke one by deleting its entry from the server's `HIPPO_AGENT_TOKEN` and redeploying — the others are unaffected. A single token (no comma) is the one-element case, fully backward-compatible.
**Instead of:** rotating the shared token on every revocation (the status quo — cheap via tooling, but couples the agents); a DB/table of tokens (over-engineered for a single-owner server — the env list is enough); iterate-all-then-OR timing (early-return leaks only *which of the owner's own* tokens matched, no value to an attacker). **Server-side only** — clients (`scripts/sync-agents.ts`, the owner's Keychain) still hold ONE token; never place the comma-list in a client's `HIPPO_AGENT_TOKEN` (it would be sent whole and rejected — fail-closed, but broken).
**Status:** active. **Where:** `src/auth/oauth.ts` `matchesAgentToken`; `tests/auth.test.ts` (+3 multi-token cases, 131 pass); `.env.example` + `SECURITY.md` + `CHANGELOG.md`. Deployed via `docker compose up -d --build`. Consumed by chief-of-staff ROADMAP #25(4) / D-006 (the dedicated box token).

### D5 · 2026-07-17 · Migrate embeddings to `@huggingface/transformers`, delete the D4 protobufjs override
**Why:** the D4 scoped override was an interim patch over the abandoned `@xenova/transformers@2.17.2` line (which pins `onnxruntime-web@1.14 → onnx-proto → protobufjs@6.11.x`). Migrating to the maintained `@huggingface/transformers@4.2.0` (same author, near-identical `pipeline` API) drops `onnx-proto` entirely; `protobufjs` now enters only via `onnxruntime-web@1.26`'s `^7.2.4` range, which resolves to the patched `7.6.5` on its own — so `npm audit` stays 0 with **no override** (the task's "onnxruntime drops protobufjs entirely" premise was slightly off — it persists but at a non-vulnerable version, unused at runtime in Node). The load-bearing risk was stored-vector compatibility (recall compares fresh query vectors against the encrypted prod DB by cosine): verified empirically that `@xenova` v2 defaulted to the **q8-quantized** model while `@huggingface` v4 defaults to **fp32**, so the embedder now pins `dtype: 'q8'` to reproduce the old vectors — min cosine **0.99955** / mean **0.99998** across a 20-string sample, and **20/20 cross-stack self-retrieval** (each new query vector retrieves its own old vector as rank-1, runner-up margin 0.54). fp32 would have drifted to ~0.99 and silently degraded recall. Measured on darwin/arm64 as a proxy for the linux/x64 prod backend — q8 integer inference is arch-stable and the 0.54 self-retrieval margin dwarfs any residual cross-arch drift, so **no re-embed needed** (final `npm ci` + native run confirmed at deploy, not against a hand-extracted prod vector). Native-binding bump (`onnxruntime-node@1.14 → 1.24.3`): the linux/x64 CPU binary ships bundled (DT_NEEDED all present in `node:20-slim`, no libgomp), but 1.24 newly auto-downloads CUDA/TensorRT GPU providers from NuGet on `linux/x64` during `npm ci` — disabled with `ENV ONNXRUNTIME_NODE_INSTALL=skip` in the Docker builder (CPU-only VPS).
**Instead of:** keeping the D4 override indefinitely (rejected — leaves the abandoned `@xenova` + `onnx-proto`/`onnxruntime-web@1.14` subtree); accepting v4's fp32 default (rejected — silent recall degradation against prod vectors); re-embedding the whole prod DB (unnecessary — the q8 pin reproduces the old vectors to cosine ≈ 1.0, not merely 384-dim-shaped). `sharp` + `onnxruntime-web` come along as dead weight (prebuilt/WASM, unused in the Node text-inference path) — accepted over fragile transitive pruning.
**Status:** active.
**Where:** `src/embeddings/embedder.ts` (dtype pin + rationale comment), `package.json` (override removed, dep swapped), `Dockerfile` (CUDA-download skip); verification harness results in the session. Supersedes D4's deferred migration follow-up; `ROADMAP.md` "Later" item cleared. VPS `npm ci`/native-build confirmed at deploy.

### D4 · 2026-07-17 · Kill the protobufjs critical with a scoped override, not a transformers downgrade/migration
**Why:** the sole Dependabot critical (protobufjs RCE, GHSA-xq3m-2v4x-88gg, vulnerable `<=7.6.2`) enters *only* through the embedder chain `@xenova/transformers@2.17.2 → onnxruntime-web@1.14.0 → onnx-proto → protobufjs@6.11.x`. `npm audit fix --force` "resolves" it by downgrading `@xenova/transformers` to 2.0.1 — which breaks embedding generation, i.e. the whole recall layer. So instead a *scoped* override — `"overrides": { "onnx-proto": { "protobufjs": "7.6.5" } }` — pins protobufjs to a patched release only under onnx-proto, leaving the embedder at 2.17.2 untouched. In Node the native onnxruntime-node backend runs inference, so the pure-JS onnx-proto/protobufjs parse path is unreachable at runtime anyway; the override exists to clear the alert, and a separate reviewer proved it load-bearing (strip it → protobufjs falls back to 6.11.6 → the critical + 3 highs return). Everything else was in-range transitives cleared by a lockfile refresh + floor-bumps (`@modelcontextprotocol/sdk ^1.29`, `hono ^4.12.30`, `@hono/node-server ^1.19.14`, `tsx ^4.23.1` → esbuild 0.28.1). Verified: `npm audit` 14→0, 128/128 tests, embedder smoke (384-dim, cosine intact), `npm ci` clean on the VPS.
**Instead of:** (a) `npm audit fix --force` — rejected, downgrades transformers 2.17.2→2.0.1 and breaks the embedder; (b) migrating to `@huggingface/transformers` *now* — the correct strategic fix (removes onnxruntime-web@1.14/onnx-proto/protobufjs entirely, no override needed) but a larger change with existing-stored-vector-compatibility risk and a native-binding bump; deferred to its own verified ROADMAP item rather than rushed into a security patch. Note: npm does **not** persist `overrides` into `package-lock.json` — `npm ci` re-reads it from `package.json` and still pins 7.6.5 (don't be alarmed that `grep overrides package-lock.json` is empty).
**Status:** superseded by D5 (2026-07-17) — the deferred migration shipped; the override is removed. D4's interim-fix reasoning stands as the record of why the critical was patched (not migrated) inside the security remediation.
**Where:** commit `c5665f3` → main, deployed + verified 2026-07-17 (`hippo.sarna.rocks/health` ok, container healthy, `sessions` gauge live); `@huggingface/transformers` migration done in D5.

### D3 · 2026-07-17 · Bound MCP session lifetime with a server-side idle sweep (OOM fix)
**Why:** the `/mcp` handler kept one fully-wired `McpServer` per session in a Map that only evicted on an explicit client `DELETE` (the SDK transport's `onsessionclosed` fires nowhere else — verified in `webStandardStreamableHttp.js`). Claude.ai and most HTTP MCP clients reconnect with a fresh session and never DELETE, so sessions accumulated across ~7 weeks of uptime until the process OOM'd at ~1.9 GB *live* heap — while the DB was only 5.8 MB, which is exactly what made it look like a query/data problem and wasn't. Fix: `src/mcp/session-registry.ts` — per-session last-seen, a 30-min idle sweep evicts inactive sessions (unref'd timer), a 1000-session LRU backstop, and an in-flight guard so a busy session is never cut mid-request; `/health` now reports the live session count for verification.
**Instead of:** raising `--max-old-space-size` / adding a container `mem_limit` (rejected — a band-aid that only delays the same OOM as sessions keep accumulating; the leak is unbounded, so any ceiling is eventually hit); relying on clients to send DELETE (not in our control). Instrument-first (per-call logging + heap snapshot) was considered but the static + SDK evidence and the 7-week-uptime→OOM profile were conclusive, so the fix shipped directly.
**Status:** active.
**Where:** commit `17147ac` (`fix/mcp-session-leak` → main), deployed + verified 2026-07-17 (`/health` `sessions` gauge live, container `RestartCount=0`); failure-mode note in CLAUDE.md → Known Gotchas.

### D2 · 2026-07-16 · Adopt the production-memory direction: append-safe writes + out-of-band curation
**Why:** the 2026-07-16 context-engineering talk (memory/versioning/dreaming at scale) names the inversion behind our own recorded failures: Hippo puts judgment in the write path (dedup-on-write deciding to replace content — which silently destroyed a dated log entry) while curation stays manual, where the production pattern is the opposite — write path dumb and deterministic (append-safe, hash-preconditioned, permission-guarded), judgment scheduled out-of-band with human-reviewed proposals. The talk also *validates* the core bet: its portability principle (files with a standalone API on top) is Hippo's thesis — the "file systems are state of the art" claim only holds when agents share a filesystem, which cross-surface agents don't. Concretely adopted: the four ROADMAP items (append-safe writes, `precondition_hash`, protected entities, mutation audit log).
**Instead of:** replacing Hippo with file-system memory (rejected — no shared filesystem across Claude.ai / ChatGPT / launchd agents; the file memory remains the in-repo arm, Hippo the cross-surface arm); observation-level version history (re-rejected — conflicts with `secure_delete`, see CLAUDE.md's entity-versioning decision; the audit log records who/when/which-entity, never content).
**Status:** active.
**Where:** `ROADMAP.md` → "Next — production-memory block"; ops-side dreaming pass in `~/chief-of-staff/ROADMAP.md` #19; AppKeep shared instance in AppKeep `DECISIONS_LOG.md` D.110.
