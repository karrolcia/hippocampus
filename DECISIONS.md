### D14 · 2026-08-26 · `recall` discloses a failed semantic leg on every response, and refuses to answer at all when the degraded answer would be empty
**Why:** `recall()` called `semanticSearch(query, opts).catch(() => [])`. Semantic search is the **primary** leg and keyword LIKE is the fallback, so any embedding failure — model load, OOM, a corrupt vector, transformers.js throwing — was swallowed and the function carried on with the weaker half of the search. The caller got `success: true` and a smaller result set with nothing anywhere to say the primary leg never ran, which makes a degraded answer indistinguishable from a complete one. At the limit it produced `success: true, count: 0`, byte-for-byte the answer for "the memory holds nothing about this". This is D13's failure family in D13's own function, one line over: quiet, in the direction of fewer results, on the read path every scheduled sweep and every briefing calls. The asymmetry inside the function was the tell — the `spread: true` branch calls `generateEmbedding` with no catch, so the identical failure was fatal there and invisible here, and nothing in the code said which was intended. The rest of the server had already voted: `remember`, `update`, `merge` and `consolidate` all call `generateEmbedding` uncaught. An embedder failure was fatal to every operation in the server **except** the two that could use it to look complete.
**Instead of:** deleting the catch so it throws like the spread branch (rejected: it is the loudest option and the one this repo's instincts pull toward, but it over-corrects. The callers that benefit from the fallback are read-only — briefings, sweeps — and they still get their keyword hits while the embedder is down. Killing that outright buys nothing the flag does not already buy, and recall is the busiest read path in the server); keeping the fallback and flagging it, with no error case (rejected: the flag rescues every cell but one. `success: true, count: 0, degraded: true` is still an empty result set, and this log has four consecutive entries of evidence that a quiet empty gets believed. Applying D10's second-order test — when you replace a bad behaviour with a report, ask what the report authorises — a degraded zero authorises nothing at all, so the only correct caller reaction is to treat it as an error, which is an argument for encoding it as one); logging server-side only (rejected as the whole fix: the app logs almost nothing per-request and request diagnostics live in Caddy's journal, so a log line reaches the operator and never reaches the caller, who is the one drawing the wrong conclusion. Kept as a component, not as the answer); unifying by making the spread branch degrade too (rejected: see below).
**The asymmetry is the decision, not an oversight.** The shared rule is that an embedding failure is always **disclosed**; what differs between the branches is what can honestly be returned instead. Without a query vector there is no dampened relationship scoring at all, so keyword-only results are not a degraded spread — they are a different operation quietly substituted for the one explicitly asked for, i.e. `spread: true` silently becoming `spread: false`. That is this entry's own failure wearing the fix's clothes. Non-spread has a real partial answer and returns it flagged; spread has none and throws. Both branches now carry the reasoning in a comment, because the next reader will otherwise find the same puzzle that started this.
**Failure direction:** degrade visibly when there is something honest to return, throw when there is not. `degraded: boolean` is on **every** recall response and `false` on the healthy path, for the same reason `remember` carries `replaced: false` (D10): a field that appears only when something went wrong cannot be told apart from an older server that never had the field, so absence must not be the all-clear. `degraded_reason` carries the error class and message, capped at 300 chars and never interpolating the query — the same string goes to the server log, and the log is the side that must not carry it. The three text formats additionally get a `DEGRADED` line prepended **inside** `text`, added only when degraded so healthy output is byte-identical: `compact`, `wire` and `index` exist to be read as text, and a disclosure sitting in a sibling JSON field the caller never opens is the same miss the field was added to close.
**Same fix, one tool over — `context`:** `context.ts` had the identical `.catch(() => [])` on its semantic leg. It is not the same case and does not get the same treatment. There the semantic search is the last leg of exact → LIKE → semantic, so when it fails there is never a partial answer to return: the only other outcome is `success: false, "No entity found for topic X"`, which is a false claim about the memory when the leg that would have found it never ran. No recoverable answer, so the catch is simply removed. Fixed here rather than filed, because leaving one of two identical swallows is precisely how D13's spread gap happened.
**Deliberate behaviour change:** a `recall` whose semantic leg fails **and** whose keyword leg matches nothing now throws and surfaces as `isError`, where it previously returned `success: true, count: 0`. This is a contract change on the busiest read path in the server and is the reason this needed its own decision rather than riding along with D13. A caller that treats any error as fatal will now fail where it used to continue — with a wrong answer it could not detect, which is the trade being made. `context` on a topic miss changes the same way: an unresolvable topic throws instead of reporting that no entity exists.
**Checked and clean:** four `.catch(...)` sites in `src` were audited, not just the reported one. `recall.ts` and `context.ts` are fixed; `index.ts`'s `backfillEmbeddings().catch()` is a deliberate boot-time log on a background task that must not take the process down, and `session-registry.ts`'s is transport cleanup with no caller to mislead. No other read path swallows an embedding failure. Recorded because "we looked" is the part that goes missing from a fix.
**Status:** active.
**Where:** `src/mcp/tools/recall.ts` (the flag, the empty-degraded throw placed before `touchRecalledObservations` so a doomed call leaves no recall-count residue, and the reasoning on both branches), `src/mcp/tools/context.ts`, `src/mcp/server.ts` (the tool description — D13's lesson is that the description string is what every client's model actually reads, so the degraded contract has to be stated there or it does not exist), `CLAUDE.md` (Key Design Decisions), `tests/recall-degraded.test.ts` (13 cases) + one healthy-path case in `tests/semantic-efficiency.test.ts`. Measured rather than assumed: **9 of 13** fail against the pre-fix `recall.ts`/`context.ts`; the 4 that pass are the two positive controls and the two behaviours this entry deliberately leaves unchanged. The failure is forced the way it actually happens — `env.allowRemoteModels = false` plus a nonexistent `localModelPath`, so the real model load fails offline and deterministically — rather than by stubbing the module, and a `poison took effect` control asserts `generateEmbedding` rejects before anything else is asserted, since every other test in the file would also pass against a working embedder.

### D13 · 2026-08-26 · `recall`'s `since` normalises the bound and rejects what it cannot parse — never an empty result set
**Why:** `created_at` is TEXT holding SQLite `datetime('now')` output, so `created_at >= ?` is a **lexicographic** comparison wearing a temporal one's clothes. ISO-8601's `T` is ASCII 0x54, above the stored space separator (0x20) and above every digit, so a `T`-separated bound sorted above every row in the table. Measured against the live server, same query and limit, only the spelling varying: `since: "2026-08-25"` → 37 results, `since: "2026-08-25 10:36:55"` → 19 results with correct time-of-day filtering, `since: "2026-08-25T10:36:55"` → **0 results, `success: true`, no error** — on the exact format the tool's own schema documented ("Only return memories after this ISO date"). The direction is what made it survive: it failed toward *absence*, on the one parameter whose entire job is answering "what landed since my last run". Every scheduled sweep — knowledge harvest, nightly session check, weekly emergence — asks that question, gets a clean success with nothing in it, and concludes nothing happened. Nothing looks broken; there is no error to notice and no log line to find. The 2026-08-25 harvest re-run nearly filed "harvest zero, nothing landed" on this basis, and what caught it was not the tool but a negative control against a boundary already known to hold data. This is the fourth entry in a row (D10, D11, D12) about a Hippocampus path that fails quietly in the direction of "there is nothing here", which is the specific failure a memory server cannot afford.
**Instead of:** making the SQL temporal — `datetime(o.created_at) >= datetime(?)` (rejected: it discards `idx_observations_created` on every filtered recall, and it fixes only the spelling half — a genuinely unparseable bound still degrades to matching nothing, which is the actual defect); documenting the working spelling and leaving validation alone (rejected: the *documented* spelling was the broken one, and the callers are language models, which will reach for ISO-8601 forever); wiring the existing `z.string().datetime()` on `recallSchema` into the live path (rejected: it is dead **and** wrong — it never ran, since `server.ts` builds its own inline schema and calls `recall()` directly, and it rejects the space-separated form that works while accepting the `T` form that does not; replaced with a plain string plus a comment naming the single validation point); normalising inside the two DB search functions (rejected: they have no error channel, so a bad bound could only be swallowed there — the contract is documented on both `SearchOptions` interfaces instead, and a test pins the raw-`T`-still-matches-nothing behaviour so the next editor finds it as documentation rather than as a surprise).
**Failure direction:** loud, deliberately. An unparseable bound now throws and surfaces as `isError` at the MCP layer, because returning nothing is indistinguishable from "nothing was stored". Format-matching alone was not enough to get there: `2026-13-01` and `2026-02-30` pass any reasonable regex and would normalise into a bound that matches nothing — the same silent zero one layer in — so every result round-trips through `Date` and must survive unchanged. The one deliberate imprecision is fractional seconds, truncated to the stored second resolution: on an *inclusive lower* bound that can only widen the window by under a second, erring toward returning an extra row rather than hiding one.
**Second fix, same family:** stored timestamps are UTC and `new Date('2026-08-25 10:36:55')` reads a zone-less string as **local** (per ES2015+ only date-only forms are UTC — the `T` separator does not change this). `recall`'s 30-day staleness hint and `consolidate`'s sleep-mode `age_days` bucketing both did that, so both were skewed by the host's offset. The production container is UTC, so today's live skew is zero — but that is a property of the deployment, not of the code: the same database answers differently on a Helsinki laptop (+3), where `scripts/sync-agents.ts` and the whole test suite run. Behaviour that depends on where the process happens to sit is the bug, whether or not it is biting.
**Checked and clean:** no other caller-supplied date is string-compared against a stored timestamp — `consolidate` takes `age_days: number`, `export` has no date filter at all. Recorded because "we looked" is the part that goes missing from a fix.
**Review round, folded in:** the separate-agent pass found one high-severity gap the first cut left open — **`spread: true` bypassed the bound entirely**. Spreading walks relationships and reads embeddings directly, so it never touches either SQL statement, and the `.describe()` text this change had just tightened to *"Only return memories at or after this UTC time"* was a promise the spread path did not keep. The shape is worse than the original bug rather than milder: spread hits are merged, re-sorted by score and sliced to `limit`, so damped out-of-window results **displace** the in-window rows that were asked for. Measured on the fixture written for it — `limit=2` → `count=2`, **`inWindow=0`**, two rows from 2020 answering a bound of 2026-08-25. An empty set at least looks empty; this looks like a healthy answer and contains nothing new, which is the same failure this entry exists to remove, wearing better clothes. Guarded now, comparing instants rather than strings (`created_at` holds ISO values from older write paths in places, and a lexicographic `>=` over a mixed column re-enters the very trap being closed), and dropping only what is *provably* before the bound so an unparseable timestamp stays visible. Four further findings closed in the same pass: the offset branch skipped validation and could emit an expanded-year bound (`+010000-01-01 04:00`) that sorts *below* every row and therefore matches everything — the same bug with the sign flipped; a fraction was accepted after `HH:MM` with no seconds, where ISO reads `.5` as thirty seconds, silently moving the bound; `consolidate` sleep mode let a NaN age skip its too-young guard and land in `prune`, i.e. proposed a deletion *because* the age could not be established; and `export`'s `split('T')[0]` returns the whole string on a space-separated timestamp, so exports printed full timestamps where a date was meant. The lesson worth keeping: **the review found the gap by checking what the fix's own new documentation now promised.** A tightened contract is a list of places to go and verify.
**Second review round:** no high-severity findings; the remaining fixes were a real coverage gap and two corrections to this session's own work. The gap: three of the round-1 fixes shipped with *no test between them* — reverting all three left the suite green, because `parseStoredTimestamp` was unit-tested while nothing asserted that `recall` and `consolidate` actually call it, and the sleep-mode NaN guard (which protects a **delete-candidate** bucket) and `export`'s date formatting had none at all. A fix nobody can regress-test is a fix with a shelf life. Separately `parseStoredTimestamp` threw on a NULL `created_at` — reachable, since the column carries no `NOT NULL` — which would have taken out an entire `recall` call or an entire sleep pass over one row, beating its own NaN backstops by one line. The correction worth recording: the review also flagged `type` as spread-unfiltered, "byte-for-byte the round-1 finding one filter over", and **that analogy is wrong** — `tests/new-features.test.ts` has pinned spreading's type-crossing as deliberate since it was written, because spreading exists to reach related entities and those are usually a different type. `since` is the opposite: a temporal bound means the same thing whichever entity a row came from. The reasoning-by-analogy was persuasive and the fix was one line; the existing test is what caught it. The real defect there was the contract text, which promised "Filter by entity type" and named no exception.
**Deliberate behaviour change:** `since: ""` used to be a silent no-op — `if (options.since)` treated it as "no bound" and returned everything — and now throws. An empty bound is almost always an unset variable interpolated by a caller, and under the old behaviour that caller got a full result set it would read as "everything is new". Erroring is the same fail-loud choice as the rest of this entry, and it is called out here because it is the one input whose *old* behaviour was not itself a silent loss. Same for truncated bounds: `since: "2026"` and `since: "2026-08"` were valid lexicographic prefixes before and now throw. A partial date is far more likely a truncation bug than an intent, and this entry's whole position is that a bound you cannot fully resolve should say so rather than quietly answer.
**Status:** active.
**Where:** `src/db/timestamps.ts` (new — `normalizeSinceBound` + `parseStoredTimestamp`, with the ASCII arithmetic written down), `src/mcp/tools/recall.ts` (normalise once, feed both legs from one variable — they run two independent SQL statements and a bound normalised in only one returns half an answer that looks like a ranking quirk), `src/mcp/tools/consolidate.ts`, `src/db/observations.ts` + `src/embeddings/embedder.ts` (contract jsdoc), `src/mcp/server.ts` (the `.describe()` string is what every client's model actually reads), `tests/recall-since.test.ts` + `tests/recall-since-spread.test.ts` + `tests/stored-timestamp-consumers.test.ts` (66 cases after two review rounds). Every one is a real regression test rather than a passing decoration, measured: against the pre-fix `recall.ts`, **9 of 54** fail in the first file and **3 of 4** in the second; against the four stored-timestamp fixes reverted together, **5 of 8** fail in the third.

### D12 · 2026-08-21 · `recall` never flags append-only entities `stale` — closing the read-path leg of the same hazard
**Why:** D10 stopped the write path deleting log entries; D11 stopped the batch path proposing their deletion. This is the third leg and the highest-frequency one: `recall` runs on every briefing and every session, where `consolidate` runs fortnightly. Its reconsolidation hint sets `stale: true` when an observation is older than 30 days **and** the entity has received newer information since — and on an active log that second clause is not a signal, it is the definition. Every historical entry qualifies, permanently. Measured against the live store before the fix: **5 of 5** recalled log observations came back `stale: true`, all on append-only entities. The hint's documented remedy is `update`, which is create-new + delete-old, so the busiest read path in the server was inviting the destruction of dated records with a 100% false-positive rate on precisely the entities D10 and D11 had just finished protecting — and CLAUDE.md's own bullet said "The AI can then use `update` to refresh stale facts", i.e. the instruction was on the record. One condition in `recall.ts` now skips append-only entities before the age test. An old log entry is not out of date; it is the entry for that date.
**Instead of:** keeping the flag and softening the documentation (rejected — this is exactly the flag-only mistake D11 rejected one tool over: the signal *is* the authorization, and prose next to it does not disarm it); adding a per-memory `append_only` marker to recall output so consumers could decide for themselves (rejected — once `stale` is gone recall's output carries no instruction at all, and a new field on every memory would tax all four formats forever, two of which exist specifically to cut tokens; `onboard`'s never-consolidate exception keys off the *remember* response, so nothing depends on it); widening the fix to `update()` itself (out of scope, and separately recorded).
**Failure direction:** safe. If the suppression is ever too broad, a genuinely outdated fact on an append-only entity merely goes unflagged — nothing can be destroyed by this change, only left un-nudged.
**Record correction:** the closing note on the D11 session said this residual was "tracked on the same ROADMAP item". It was not — the ROADMAP paragraph mentions `stale` only as a *consequence* of one day fixing `update()`'s `created_at` reset, not as an item of its own. It is recorded here instead.
**Review note folded in:** `isAppendOnlyEntity`'s docblock enumerates its consumers — D11 started that list when it added the second — and this commit added a third without updating it, which is how the next editor comes to widen the prefix list without realising staleness suppression rides on it. The docblock now lists all three legs, the config comment no longer says "exempt from dedup-on-write" as though that were the only behaviour, and the README's env-var bullet cross-references all three (a self-hoster setting `none` to disable dedup exemptions was otherwise silently re-enabling permanent stale-flagging on every log entity, with the explanation in a different section).
**Status:** active.
**Where:** `src/mcp/tools/recall.ts` (one condition + the reasoning), `src/config.ts` (consumer list), CLAUDE.md "Reconsolidation hints" bullet (it carried the instruction, so it had to carry the exemption), README, `tests/memory-lifecycle.test.ts` — the new test's control is the pre-existing "old observation on updated entity → stale = true" case, identical shape on an ordinary entity. Drive-by in the path of work: that control asserted inside `if (oldMemory) { … }`, so it passed vacuously whenever recall failed to return the observation — the exact condition it exists to detect. Now asserted unconditionally (and it does pass). 181 tests.

### D11 · 2026-08-21 · `consolidate` excludes append-only entities from all four modes — exclusion with disclosure, not a flag
**Why:** D10 stopped `remember` from silently evicting dated log entries and closed the second-order hole where the *response* invited the model to delete them by hand. It did nothing about `consolidate`, which is the same hazard one tool over and arguably the more direct one: `consolidate` proposes, and `merge` / `merge_entities` / `update` dispose. Measured, not assumed: two consecutive knowledge-harvest entries cluster at **0.948** against the 0.8 default, returned with full content + observation ids under the message "Review each cluster and use merge to consolidate"; `mode: "sleep"` buckets never-recalled observations older than 30 days as `prune`, which describes the entire `ops:daily-log:*` history (a daily log is recalled semantically across entries, essentially never as an individual observation); and `entities` mode scores `ops:daily-log:codesea` against `ops:daily-log:rsl-content` at **0.688**, a whisker under the 0.7 default — one threshold tweak from proposing that two different projects' logs are the same entity, which `merge_entities` would then fold together (no observation deleted, but the per-context separation the whole logging convention rests on, gone). On a log entity every one of these proposals is a false positive **by construction**: two dated entries sharing a template are not duplicates, and an old never-recalled log entry is not dead weight, it is the record. So all four modes now filter through `isAppendOnlyEntity` before any math, the drop is counted in `excluded_append_only` and named in the message, and an entity-scoped call on a log entity says *why* it is empty rather than returning a bare "No observations found" — that reassuring-silence shape is the reason this saga needed a D10 at all. `include_append_only: true` is the deliberate escape hatch for the one genuine case: hunting accidental double-writes, which D10 made *more* likely by removing dedup from these entities entirely. Its failure direction is safe — Zod strips an unknown arg, so a malformed call degrades toward exclusion, and no `STRICT_TOOLS` entry is needed.
**Instead of:** **flag-only** — annotating members with `append_only: true` and leaving them in the results (this was the fix shape the D10 reviewer proposed and the ROADMAP recorded, so the divergence is deliberate: a flagged cluster still ships full content plus observation ids next to "use merge to consolidate", which is exactly the loaded-gun shape D10 had to remove from `remember`'s response, and the `onboard` exception written in D10 covers `remember` responses, not `consolidate` output; separately, a `prune` list dominated by log entries buries the genuine candidates, the cried-wolf failure mode LB10 names); excluding only from `prune` (rejected — `compress` proposes `merge`, and `refresh` proposes `update`, which is create-new + delete-old and so rewrites a dated entry); widening `HIPPO_APPEND_ONLY_PREFIXES` to match the ops-side `NEVER_PRUNE_PREFIXES` list in `~/chief-of-staff/dreaming/digest.py`, which is broader (`agent:`, `raw:`, `artifact:`, `call:`, `compiled:`, …) — rejected because the two lists encode *different* policies and both are right for their layer: the server's means "these are logs, entries are not duplicates, exempt from dedup", the client's means "never delete these on age". Conflating them would silently change `remember`'s dedup behaviour for `agent:`/`raw:`/`artifact:` entities, which nothing asked for.
**Two deliberate consequences**, named so they are not read as regressions: sleep's SVD basis is now computed over the consolidatable population only, so `information_rank` / `redundancy_ratio` change value (an improvement — shared log skeletons were inflating store-wide redundancy — but a visible number change); and a normal observation that clustered only *via* an append-only bridge node no longer clusters, which is correct, since a merge proposal routed through an unmergeable bridge was incoherent.
**Consumer check before deploy:** `~/chief-of-staff/dreaming/digest.py` (the fortnightly `com.karolina.dreaming` pass) already applies its own client-side `is_never_prune` guard to `prune` and `compress`, so the live exposure was smaller than D10's write-up implied — worth correcting the record. It is not made redundant: its list is broader than the server's three prefixes, so `prune_excluded_audit_trail` stays non-zero and the counter will not read as a broken guard. Nothing in `run.sh` asserts a non-empty prune list, so the shape change cannot fail the pass closed.
**Review loop folded in (separate-agent, CHANGES-REQUIRED → fixed):** three findings. (1) **Blocker:** `entities` mode declared `EntityClusterMember.append_only` and never assigned it — a dead field, which is the tell that it was an oversight rather than a decision. Under `include_append_only` the response therefore listed two log entities as merge candidates with no marker at all, on the one mode whose disposal tool (`merge_entities`) deletes the source entity and folds two projects' whole log histories together — and `append_only: true` is precisely the signal `onboard`'s never-merge exception keys off. The D10 lesson restated: when you replace a destructive behaviour with a report, check what the report authorises. (2) `include_append_only` was never registered in `param-normalization.ts`'s consolidate param set, so a client sending the camelCase `includeAppendOnly` had it stripped by Zod and the escape hatch silently no-op'd (fails safe — exclusion still applies — but silently). (3) The contradictions test asserted `pairs.length === 0` on a fixture that **would never have paired anyway**: the predicate needs high embedding similarity AND low lexical overlap, and two log entries worded differently enough to clear `jaccard < 0.3` have drifted too far apart in embedding space to clear 0.6. The assertion passed whether or not the filter existed. Replaced with a 0.521/0.000 pair at an explicit `threshold: 0.45`, plus a control proving it does pair when included — the mutation that switches the filter off now kills that test too.
**Second review pass (APPROVE-WITH-NITS, all four folded in):** (1) the sleep-mode `append_only` marker was the one disposal path with no assertion — deleting it left all 179 tests green, the same declared-but-unverified shape as the iteration-1 blocker, now covered; (2) under the hatch `excluded_append_only` is 0, so the disclosure note is empty and the response carried "use merge to consolidate" with no prose signal at all — the per-member flag was the only counter-signal. Added `includedAppendOnlyCaveat`, emitted by all four modes whenever a returned member is append-only, saying plainly that dated log entries are not duplicates of each other. (3) The contradictions test drove `threshold: 0.45`, below the MCP schema's `.min(0.5)` — an input no client can send; moved to 0.5 (measured pair is 0.521, so 0.021 headroom, and the CONTROL fails loudly if the model drifts). (4) One assertion matched `/^No observations found\.$/`, a string that exists nowhere in `src/` — it could never fire; replaced with the string the code actually emits.
**Status:** active.
**Where:** `src/mcp/tools/consolidate.ts` (four modes + `excludeAppendOnly` + `include_append_only`), `src/config.ts` (`isAppendOnlyEntity` moved here from `remember.ts` — it is now shared by two tools; the `.trim()` from the D10 review travels with it), `src/mcp/server.ts` (schema param + description — the LLM reads the description, not the README), `src/mcp/param-normalization.ts` (the new param registered in consolidate's leniency set), `tests/consolidate-append-only.test.ts` (10 tests) + one normalizer test, 180 total. Every exclusion test is paired with a CONTROL asserting the same fixture IS proposed on an ordinary entity or under `include_append_only`, so it fails if the fixture stops being something consolidate would have proposed; neutralising the filter kills 5 of the 10. Note the control fixtures needed backdating — written the same day, D10's own dedup replaced the first entry with the second and the control quietly degraded to a single observation.

### D10 · 2026-08-21 · Bound dedup-on-write with an append-only exemption + same-UTC-day scoping, rather than demoting replace-to-flag globally
**Why:** `remember`'s dedup deletes the stored observation when a new one scores >= 0.85 cosine and is longer. On append-only entities that is a live data-loss path, not a theoretical one — four confirmed evictions (2026-07-09 harvest entry; `ops:daily-log:nightly-check` 06-01, restored by hand; a `synthesis:ingest-backlog` correction eating the very observation it corrected at 0.867, 08-14; and 08-21, a 9,197-char harvest entry evicting the 6,182-char 07-31 entry on `ops:daily-log:hippocampus` — written three weeks apart, substantively unrelated, carried over the threshold purely by the shared harvest-log skeleton). Two guards, because neither alone is sufficient and the required regression tests prove it: **(a)** entity names matching a `HIPPO_APPEND_ONLY_PREFIXES` prefix (default `ops:daily-log:`, `ops:session-check`, `synthesis:`) are exempt from dedup entirely — a correction is usually written the *same day* as its target, so only the exemption saves the 08-14 shape; **(b)** everywhere else dedup considers only same-UTC-calendar-day observations, which protects the log entities nobody remembered to list, the 08-21 shape. Both arms are gated, not just the delete: a skip loses the *new* entry, which for a log is the same wound reversed. **Calendar-day equality, not a rolling N-hour window** — a rolling window fails destructively at midnight (23:58 and 00:05 are seven minutes apart and two different days' entries), day equality fails safe (worst case a duplicate is stored; that is what `consolidate` is for), and it needs no date parsing at all: `created_at` is `datetime('now')` UTC, so the gate is a `slice(0,10)` string compare, which also sidesteps the known UTC-vs-local parsing trap. **Second half of the fix is visibility.** The reason this ran undetected through four incidents is that >= 0.85 matches went to the dedup branch and only 0.5–0.85 to `near_matches` — so a caller checking `near_matches` saw an empty list at the exact moment data died, while the eviction was announced only in the prose `message` and `replaced_observation` (both routinely dropped when parsing a field subset). The reliable detector was an observation-count diff, which no caller ran. So: guard-blocked matches now surface in `near_matches`, and every destructive result sets a top-level `replaced: true` with `replaced_observation` + `replaced_observation_id` (`replace_kind` reports `replaced` + `replaced_count`).
