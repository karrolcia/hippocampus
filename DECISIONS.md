### D10 · 2026-08-21 · Bound dedup-on-write with an append-only exemption + same-UTC-day scoping, rather than demoting replace-to-flag globally
**Why:** `remember`'s dedup deletes the stored observation when a new one scores >= 0.85 cosine and is longer. On append-only entities that is a live data-loss path, not a theoretical one — four confirmed evictions (2026-07-09 harvest entry; `ops:daily-log:nightly-check` 06-01, restored by hand; a `synthesis:ingest-backlog` correction eating the very observation it corrected at 0.867, 08-14; and 08-21, a 9,197-char harvest entry evicting the 6,182-char 07-31 entry on `ops:daily-log:hippocampus` — written three weeks apart, substantively unrelated, carried over the threshold purely by the shared harvest-log skeleton). Two guards, because neither alone is sufficient and the required regression tests prove it: **(a)** entity names matching a `HIPPO_APPEND_ONLY_PREFIXES` prefix (default `ops:daily-log:`, `ops:session-check`, `synthesis:`) are exempt from dedup entirely — a correction is usually written the *same day* as its target, so only the exemption saves the 08-14 shape; **(b)** everywhere else dedup considers only same-UTC-calendar-day observations, which protects the log entities nobody remembered to list, the 08-21 shape. Both arms are gated, not just the delete: a skip loses the *new* entry, which for a log is the same wound reversed. **Calendar-day equality, not a rolling N-hour window** — a rolling window fails destructively at midnight (23:58 and 00:05 are seven minutes apart and two different days' entries), day equality fails safe (worst case a duplicate is stored; that is what `consolidate` is for), and it needs no date parsing at all: `created_at` is `datetime('now')` UTC, so the gate is a `slice(0,10)` string compare, which also sidesteps the known UTC-vs-local parsing trap. **Second half of the fix is visibility.** The reason this ran undetected through four incidents is that >= 0.85 matches went to the dedup branch and only 0.5–0.85 to `near_matches` — so a caller checking `near_matches` saw an empty list at the exact moment data died, while the eviction was announced only in the prose `message` and `replaced_observation` (both routinely dropped when parsing a field subset). The reliable detector was an observation-count diff, which no caller ran. So: guard-blocked matches now surface in `near_matches`, and every destructive result sets a top-level `replaced: true` with `replaced_observation` + `replaced_observation_id` (`replace_kind` reports `replaced` + `replaced_count`).
**Instead of:** the ROADMAP's stated done-condition — demoting replace to flag *globally*, so no code path ever replaces without `replace_kind` (**not taken, and the item stays open**: this session's brief scoped the fix to the log-entity failure, and removing same-day replace everywhere changes ordinary fact-entity behaviour — an AI restating one fact with more detail in one session — that has never been implicated in a loss; the guards close the data-loss path, the global demotion remains a separate call about how dumb the write path should be); a rolling `HIPPO_DEDUP_WINDOW_HOURS` window (rejected — destructive midnight failure, plus a "0 means what?" ambiguity in the knob); a hardcoded prefix list (rejected — a self-hosted deployment with different log naming would need a code change; unset *or blank* gives the defaults and the literal `none` disables, because compose's `${VAR:-}` idiom forwards an unset variable as `""` and blank-means-off would have unprotected prod the moment the var was merely forwarded); matching on entity `type` instead of name prefix (rejected — `type` is optional and inconsistently set by callers, so it would silently protect nothing).
**Review loop folded in (separate-agent, APPROVE-WITH-NITS):** five real findings, all fixed in the same branch. (1) The knob was inert on the actual deployment — `docker-compose.yml`'s `environment:` block is allowlist-based (the repo's own gotcha), so `HIPPO_APPEND_ONLY_PREFIXES` never reached the container; adding it exposed the trap that the house `${VAR:-}` idiom forwards unset as `""`, which under the first draft's semantics meant *no exemptions* — i.e. wiring up the knob would have disabled protection on prod. Hence blank-means-defaults with an explicit `none`. (2) `replace_kind` deleted N observations and returned a count only, no recoverable content — the widest blast radius of any `remember()` path with the weakest reporting; it now returns `replaced_observations` (ids + full text) and flags `append_only`. (3) A leading space in the entity name defeated the prefix guard entirely — names are stored verbatim and matched exactly, so `" synthesis:x"` is a distinct entity that `startsWith` missed, reopening the exact 2026-08-14 shape; the guard now trims before matching. (4) A malformed separator (`;` for `,`) silently collapsed the list to one garbage prefix and unprotected everything, with no signal — the resolved list is now logged at startup. (5) Noted-not-fixed: `update()` implements edit as create-new + delete-old, so editing an old observation stamps it with today's `created_at` and re-arms cross-day eviction on non-exempt entities — recorded on the open ROADMAP item, which dissolves it.
**Second review pass — the one that mattered:** the branch satisfied every acceptance criterion *as written* while defeating the intent behind one of them. Criterion (c) asked for held-back overlap to be **visible**; visibility had been implemented as the existing "consider consolidating" nudge, and `near_matches[].content` is byte-identical to the stored observation — which is exactly the key `update` matches on (`o.content === old_content`). Meanwhile `onboard`'s standing instruction is "novelty < 0.3 + high overlap → `update`, or `merge` if multiple cluster". So on every daily-log write the server now preserved the old entry (guard working, `replaced: false`) and then handed the AI a loaded gun plus the ammunition: measured 0.99 similarity, novelty 0.129, three full prior entries quoted back, and an instruction to consolidate them. Same data loss, one layer up, on the hot path — and it would have looked like the fix working. Closed three ways: on append-only entities `near_matches` content is truncated to a 200-char preview (deliberately non-executable — a stray `update` now fails safe with "No observation matching the old content found", proved by a test that actually attempts it), the message says "Do NOT consolidate, update or merge them" instead of inviting it, and `onboard` step 4 gained an explicit `append_only` exception. Full content is retained on non-append-only entities, where consolidation IS the intended workflow and needs the exact key. Also fixed: a comma-only value (`,`) parsed to an empty list and silently disabled protection, which is the one thing the `none` sentinel exists to make deliberate.
**Status:** active.
**Where:** `src/mcp/tools/remember.ts` (guards + `replaced` flag), `src/config.ts` (`parseAppendOnlyPrefixes`, `DEFAULT_APPEND_ONLY_PREFIXES`), `docker-compose.yml` (the `environment:` allowlist — a knob the container never sees is not a knob), `src/index.ts` (resolved list logged at startup, so a typo'd separator is visible instead of silently unprotecting everything), `src/mcp/server.ts` (the `remember` description tells the LLM caller that a write can delete), `.env.example`, `tests/append-only-dedup.test.ts` + `tests/append-only-config.test.ts` (22 tests, 169 total). Every survival test asserts its fixture pair actually clears 0.85 before asserting survival — a regression test that passes on a pair the old code would never have touched proves nothing, and the first draft's correction fixture measured 0.703 and was caught by exactly that assertion. Verified against the pre-fix path by neutralising the guards: 9 of the 22 new tests fail, all pass with them; each leg of the fix (exemption, day-scoping, `near_matches` reporting, preview truncation, the `onboard` exception) was separately mutated and has a test that kills it.

### D7 · 2026-07-27 · `forget` gets content-scoped deletion + strict argument rejection; `update` preserves observation metadata
**Why:** two observation-scoping bugs surfaced while syncing edited pseo skills. (1) `update` rebuilt the replacement observation with only `content` + `source`, dropping `kind` (→ null) and `importance` (→ 1.0); an explicit `kind` arg was silently stripped by Zod. Fixed by carrying both over from the old observation, with an optional `kind` param to set/re-tag. (2) `forget({entity, content})` deleted the WHOLE entity: Zod *strips* unknown keys rather than rejecting, so the call degraded to `forget({entity})` — a scoped delete silently widening to a full delete (destroyed `skill:pseo-llm-visibility`, 2 obs + 2 embeddings + 2 rels). Fixed twice over: `content` is now a real param (exact-match one observation, delete only it, a miss deletes nothing), and `forget` is registered in a `STRICT_TOOLS` set in `param-normalization.ts` — unrecognized args throw a descriptive error (key name only, never the value — content must not leak into error responses) instead of passing through to Zod's strip. The client-side twin table in `~/chief-of-staff/hippo-query.sh` learned both params the same day. Precedence when multiple scopes given: `observation_id` > `content` > entity-wide.
**Instead of:** rejecting `content` as unknown and keeping forget two-mode (rejected — the scoped delete is what callers actually mean, and update's exact-content-match sets precedent); making ALL tools strict (rejected — read-path tools lose nothing to a stripped key, and blanket strictness would break lenient callers the normalization layer exists to serve); `.strict()` Zod schemas (rejected — `server.tool()` takes a raw shape, and the known `normalizeObjectSchema` gotcha makes wrapper types hazardous; the request-handler boundary is the established interception point).
**Status:** active.
**Where:** `src/mcp/tools/{update,forget}.ts`, `src/mcp/server.ts` (schemas), `src/mcp/param-normalization.ts` (`STRICT_TOOLS`), `tests/observation-scoping.test.ts` (12 tests), CHANGELOG Unreleased. Includes drive-by fix: `forget` by `observation_id` now calls `updateEntityTimestamp` (version_hash was going stale).

### D6 · 2026-07-21 · `HIPPO_AGENT_TOKEN` accepts a comma-separated list (per-agent revocable tokens)
**Why:** the estate now has two self-hosted machine-to-machine agents — Karolina's Mac and the ops-backbone loops box — sharing one static agent token. Sharing means revoking one (e.g. the internet-facing box, if compromised) forces rotating the other. So `matchesAgentToken` now splits `config.agentToken` on `,`, trims each entry, enforces the 32-char floor **per token** (previously only the whole value was floor-checked), and timing-safe-compares the candidate against each (returns on first match; a non-match still iterates every entry, so failed guesses are position-independent in time). Each agent holds its own token; revoke one by deleting its entry from the server's `HIPPO_AGENT_TOKEN` and redeploying — the others are unaffected. A single token (no comma) is the one-element case, fully backward-compatible.
**Instead of:** rotating the shared token on every revocation (the status quo — cheap via tooling, but couples the agents); a DB/table of tokens (over-engineered for a single-owner server — the env list is enough); iterate-all-then-OR timing (early-return leaks only *which of the owner's own* tokens matched, no value to an attacker). **Server-side only** — clients (`scripts/sync-agents.ts`, the owner's Keychain) still hold ONE token; never place the comma-list in a client's `HIPPO_AGENT_TOKEN` (it would be sent whole and rejected — fail-closed, but broken).
**Status:** active. **Where:** `src/auth/oauth.ts` `matchesAgentToken`; `tests/auth.test.ts` (+3 multi-token cases, 131 pass); `.env.example` + `SECURITY.md` + `CHANGELOG.md`. Deployed via `docker compose up -d --build`. Consumed by chief-of-staff ROADMAP #25(4) / D-006 (the dedicated box token).

### D5 · 2026-07-17 · Migrate embeddings to `@huggingface/transformers`, delete the D4 protobufjs override
**Why:** the D4 scoped override was an interim patch over the abandoned `@xenova/transformers@2.17.2` line (which pins `onnxruntime-web@1.14 → onnx-proto → protobufjs@6.11.x`). Migrating to the maintained `@huggingface/transformers@4.2.0` (same author, near-identical `pipeline` API) drops `onnx-proto` entirely; `protobufjs` now enters only via `onnxruntime-web@1.26`'s `^7.2.4` range, which resolves to the patched `7.6.5` on its own — so `npm audit` stays 0 with **no override** (the task's "onnxruntime drops protobufjs entirely" premise was slightly off — it persists but at a non-vulnerable version, unused at runtime in Node). The load-bearing risk was stored-vector compatibility (recall compares fresh query vectors against the encrypted prod DB by cosine): verified empirically that `@xenova` v2 defaulted to the **q8-quantized** model while `@huggingface` v4 defaults to **fp32**, so the embedder now pins `dtype: 'q8'` to reproduce the old vectors — min cosine **0.99955** / mean **0.99998** across a 20-string sample, and **20/20 cross-stack self-retrieval** (each new query vector retrieves its own old vector as rank-1, runner-up margin 0.54). fp32 would have drifted to ~0.99 and silently degraded recall. Measured on darwin/arm64 as a proxy for the linux/x64 prod backend — q8 integer inference is arch-stable and the 0.54 self-retrieval margin dwarfs any residual cross-arch drift, so **no re-embed needed** (final `npm ci` + native run confirmed at deploy, not against a hand-extracted prod vector). Native-binding bump (`onnxruntime-node@1.14 → 1.24.3`): the linux/x64 CPU binary ships bundled (DT_NEEDED all present in `node:20-slim`, no libgomp), but 1.24 newly auto-downloads CUDA/TensorRT GPU providers from NuGet on `linux/x64` during `npm ci` — disabled with `ENV ONNXRUNTIME_NODE_INSTALL=skip` in the Docker builder (CPU-only VPS).
**Instead of:** keeping the D4 override indefinitely (rejected — leaves the abandoned `@xenova` + `onnx-proto`/`onnxruntime-web@1.14` subtree); accepting v4's fp32 default (rejected — silent recall degradation against prod vectors); re-embedding the whole prod DB (unnecessary — the q8 pin reproduces the old vectors to cosine ≈ 1.0, not merely 384-dim-shaped). `sharp` + `onnxruntime-web` come along as dead weight (prebuilt/WASM, unused in the Node text-inference path) — accepted over fragile transitive pruning.
**Status:** active.
**Where:** `src/embeddings/embedder.ts` (dtype pin + rationale comment), `package.json` (override removed, dep swapped), `Dockerfile` (CUDA-download skip); verification harness results in the session. Supersedes D4's deferred migration follow-up; `ROADMAP.md` "Later" item cleared. VPS `npm ci`/native-build confirmed at deploy.

### D4 · 2026-07-17 · Kill the protobufjs critical with a scoped override, not a transformers downgrade/migration
**Why:** the sole Dependabot critical (protobufjs RCE, GHSA-xq3m-2v4x-88gg, vulnerable `<=7.6.2`) enters *only* through the embedder chain `@xenova/transformers@2.17.2 → onnxruntime-web@1.14.0 → onnx-proto → protobufjs@6.11.x`. `npm audit fix --force` "resolves" it by downgrading `@xenova/transformers` to 2.0.1 — which breaks embedding generation, i.e. the whole recall layer. So instead a *scoped* override — `"overrides": { "onnx-proto": { "protobufjs": "7.6.5" } }` — pins protobufjs to a patched release only under onnx-proto, leaving the embedder at 2.17.2 untouched. In Node the native onnxruntime-node backend runs inference, so the pure-JS onnx-proto/protobufjs parse path is unreachable at runtime anyway; the override exists to clear the alert, and a separate reviewer proved it load-bearing (strip it → protobufjs falls back to 6.11.6 → the critical + 3 highs return). Everything else was in-range transitives cleared by a lockfile refresh + floor-bumps (`@modelcontextprotocol/sdk ^1.29`, `hono ^4.12.30`, `@hono/node-server ^1.19.14`, `tsx ^4.23.1` → esbuild 0.28.1). Verified: `npm audit` 14→0, 128/128 tests, embedder smoke (384-dim, cosine intact), `npm ci` clean on the VPS.
**Instead of:** (a) `npm audit fix --force` — rejected, downgrades transformers 2.17.2→2.0.1 and breaks the embedder; (b) migrating to `@huggingface/transformers` *now* — the correct strategic fix (removes onnxruntime-web@1.14/onnx-proto/protobufjs entirely, no override needed) but a larger change with existing-stored-vector-compatibility risk and a native-binding bump; deferred to its own verified ROADMAP item rather than rushed into a security patch. Note: npm does **not** persist `overrides` into `package-lock.json` — `npm ci` re-reads it from `package.json` and still pins 7.6.5 (don't be alarmed that `grep overrides package-lock.json` is empty).
**Status:** superseded by D5 (2026-07-17) — the deferred migration shipped; the override is removed. D4's interim-fix reasoning stands as the record of why the critical was patched (not migrated) inside the security remediation.
**Where:** commit `c5665f3` → main, deployed + verified 2026-07-17 (`hippo.sarna.rocks/health` ok, container healthy, `sessions` gauge live); `@huggingface/transformers` migration done in D5.

### D3 · 2026-07-17 · Bound MCP session lifetime with a server-side idle sweep (OOM fix)
**Why:** the `/mcp` handler kept one fully-wired `McpServer` per session in a Map that only evicted on an explicit client `DELETE` (the SDK transport's `onsessionclosed` fires nowhere else — verified in `webStandardStreamableHttp.js`). Claude.ai and most HTTP MCP clients reconnect with a fresh session and never DELETE, so sessions accumulated across ~7 weeks of uptime until the process OOM'd at ~1.9 GB *live* heap — while the DB was only 5.8 MB, which is exactly what made it look like a query/data problem and wasn't. Fix: `src/mcp/session-registry.ts` — per-session last-seen, a 30-min idle sweep evicts inactive sessions (unref'd timer), a 1000-session LRU backstop, and an in-flight guard so a busy session is never cut mid-request; `/health` now reports the live session count for verification.
**Instead of:** raising `--max-old-space-size` / adding a container `mem_limit` (rejected — a band-aid that only delays the same OOM as sessions keep accumulating; the leak is unbounded, so any ceiling is eventually hit); relying on clients to send DELETE (not in our control). Instrument-first (per-call logging + heap snapshot) was considered but the static + SDK evidence and the 7-week-uptime→OOM profile were conclusive, so the fix shipped directly.
**Status:** active.
**Where:** commit `17147ac` (`fix/mcp-session-leak` → main), deployed + verified 2026-07-17 (`/health` `sessions` gauge live, container `RestartCount=0`); failure-mode note in CLAUDE.md → Known Gotchas.
