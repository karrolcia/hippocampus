### D26 · 2026-10-22 · Rate-limit the OAuth routes per client address plus one global failed-login cap, key on the proxy-written `X-Forwarded-For` hop only, and cap OAuth bodies at 16 KB
*Numbering: D25 is claimed by the held `prod-check-2026-10-22` branch (the report that found this); this takes D26. Whichever lands second renumbers.*
**Why:** prod-check 2026-10-22 AUTH-05: the only limiter was on `/mcp`, so the one password could be guessed online without limit against the form that issues a 30-day refresh token. Limits are login-shaped and per method (`oauth.post(path, limiter, ...)`, so rendering the GET form spends nothing): `POST /authorize` 10/15 min, `POST /token` 30/15 min, `POST /register` 10/hour, all far below `/mcp`'s 60/min. A per-address limit alone is beaten by address rotation, so wrong passwords also feed one global counter (20/hour), checked before the body is parsed and incremented only on the 401 branch. The tradeoff, accepted: anyone can lock the owner out of NEW logins for up to an hour. `/token` is left outside the lockout, so existing sessions refresh through it, and a restart clears it. Not guessing faster than 20 passwords an hour outweighs a lockout that costs a re-auth delay. The key: `X-Forwarded-For` is read only when the TCP peer is loopback/private (prod sees the docker bridge gateway `172.18.0.1`), and then only its rightmost entry, the one the proxy wrote. Prod was not exploitable: the live Caddy has no `trusted_proxies` and replaces the header, which the reviewer measured. The raw-header key was safe only because of Caddy, and any self-hoster exposing the port directly could forge a fresh counter per request. The 16 KB `bodyLimit` (WEB-01's pre-auth leg) runs after the limiter and before any parse, so no pre-auth request makes the process buffer an unbounded body. The limits are hard-coded, not env: compose forwards an unset var as `""` and `z.coerce.number("")` is 0, which would refuse every login. Dead `RATE_LIMIT_REMEMBER` (parsed, never read) removed, and the README/SECURITY.md claims ("rate limiting on all endpoints", per-tool limits, a 10 KB cap, an observation cap) now describe what exists.
**Instead of:** a raw `X-Forwarded-For` key (forgeable whenever no proxy rewrites it); the socket peer only (behind docker-proxy every client is `172.18.0.1`, so `/mcp`'s 60/min would be shared by all clients); the leftmost XFF entry (client-controlled behind an appending proxy); a `TRUST_PROXY` env knob (one more var compose forwards as `""`; the private-peer rule covers Caddy-on-host, Docker networks and Fly without configuration); per-address limits only (beaten by IPv6 rotation, as the report says); env-configurable OAuth limits (the `""`→0 trap above); the rest of WEB-01 (zod schemas, a `redirect_uris` cap, client expiry) in this change (not a few lines; it touches `/register` alongside the open phish item, so it is a ROADMAP item paired with that one).
**Status:** active.
**Where:** `src/middleware/rate-limit.ts` (`clientAddress`, `isTrustedProxyPeer`, `createFailureCounter`), `src/auth/oauth.ts` (`OAUTH_LIMITS`, `OAUTH_BODY_LIMIT_BYTES`), `tests/oauth-rate-limit.test.ts` (21 tests; 10 injected mutations each turned the named test red); ROADMAP → Next (WEB-01 remainder) and the 2026-10-22 watch list.

### D23 · 2026-09-09 · Add `get_observation` — the id-taking read that was missing, bounded to one row and holding no write
**Why:** Observation ids are handed out by three tools — `remember` returns `observationId`, `recall` returns `observation_id` per memory **in `format: "full"` only** (`compact`/`wire`/`index` return a text blob with no ids), and `export` emits them **in `format: "json"` only**. D20 adds a fourth — `remember`'s `near_matches[].observation_id`, on ordinary entities only — and it landed on `origin/main` while this branch was in review; see the landing note at the end. Both tools that ACCEPT an id destroy rows: `forget` deletes the row, and `merge` deletes every source it is given and keeps only the text the caller composes. **Nothing read by id.** That is the D10 shape one tool over — a key that destroys, handed out beside 200 of the ~45,000 chars it names, with no bounded way to see the rest before using it.
**The prescribed workaround does not hold at the sizes that produced it, and this was measured rather than argued.** Re-verified independently on this branch against a fixture of 45,000-char siblings backdated to distinct days (six rows in the scratch measurement, five in the committed test, which only needs enough to make `recall` overshoot): `recall({query: <the preview>, format: "full"})` at the default limit returns **272,272 chars** — 2.4x the 115,271-char response the cap exists to eliminate — and `recall(..., limit: 1)` returns 45,442 chars of the **wrong sibling** (the target ranked 4 of 6). The similarity floor is not the problem, and the figure here is one this branch measured rather than one carried across from the round-two review: embedding the six ledger parts and comparing them pairwise gives **0.847–0.976** across all 15 pairs, far above `SIMILARITY_THRESHOLD = 0.15`. Near matches cluster on a shared skeleton by construction — D10's own mechanism — so the siblings are nearly indistinguishable to the scorer and ranking, not the floor, decides which one comes back. (A separate preview-against-sibling figure appeared in the round-two review; it is not reproduced here because this entry should only cite what it ran. Reproduce with `generateEmbedding` + `cosineSimilarity` over the `ledgerPart` fixture in `tests/get-observation.test.ts`.) And `recall` is a **WRITE** — `touchRecalledObservations` bumped `recall_count` on all six rows across three fetches — so the step prescribed as a read was feeding decay-weighted retrieval and sleep-mode `prune` classification on rows the caller was about to merge away. No other tool fills the gap: `context`'s `formatObs` returns no observation id at all (and is the documented token-cap blowup on exactly these entities), `export` is per-entity and unbounded, `forget` is id-native and deletes.
**What it buys, and the boundary it does NOT move — this is the part a later reader most needs.** `merge`'s `content` is capped at `.max(50000)` at the wire boundary in `src/mcp/server.ts`, the same cap `remember` enforces. So two 45,000-char rows can now be **read** and still cannot be **combined** without discarding roughly 40,000 chars of source. The fetch separates two things the deferral conflated: **readability**, which is fixable and is fixed here, and **mergeability**, which is a real cap no tool changes. The honest consolidation boundary is therefore not "report-only above a few thousand chars" but **"consolidate only when the combined text fits under 50,000"** — a better boundary because it names the actual constraint and the caller can evaluate it. This also reframes the primary value: at 45,000 chars the correct answer is usually *these are distinct parts of a ledger, do not merge*, and reaching that answer previously cost a 272,272-char response that also mutated six rows' access telemetry. The fetch makes the correct non-destructive decision cheap, which is the opposite of the concern that deferred it.
**Instead of:** (a) *Not building it, on the grounds that report-only is the right behaviour at that size* — rejected, and the reason is that the argument is against a **use**, not against the **primitive**. "Merging two 45,000-char rows is a bad idea" is true, and the merge cap above now enforces it independently. It says nothing about a caller's need to see what an id addresses before calling `forget` on it. Left unbuilt, the state shipped is a destruction key with no matching read key, which the D10–D12 line exists to prevent. (b) *An `observation_id` param on `context`* — rejected: it would make `context`'s scope depend on which argument is present, which is precisely the shape that put `forget` in `STRICT_TOOLS`, and `context` is already the documented token-cap blowup on large entities. (c) *An `observation_ids` param on `export`* — rejected: `export` is a backup/serialization surface keyed by `format`, and a targeted single-row read has no meaningful answer for "as an Obsidian vault". Overloading it confuses both jobs. (d) *An MCP **resource**, `hippocampus://observation/{id}`* — the idiomatic read shape, and rejected on deployment reality: connector support for resource templates is not universal across the clients this server targets, and the caller here is a model mid-workflow, which reaches for tools. (e) *Accepting an array of ids* — rejected as unbounded-by-degrees: N x 50,000 needs its own count cap and a total-size story, while a single id is bounded by a cap that already exists. A two-id merge costs two calls and the same total bytes.
**Bounded means bounded by construction, and the bound is on the ROW, not on the response.** Exactly the one row named, and a row cannot exceed the 50,000-char cap `remember` enforces on write. The serialized response is larger, because JSON escaping inflates content by an amount that depends entirely on what the content is. Measured on 45,000-char inputs: **1.003x** on this repo's own prose and **1.014x** on a log with a newline every ~70 chars — the shapes real memories actually take — rising to **1.20x** on a synthetic string with a newline every 5, and a ceiling of **2.01x** on 50,000 quote or backslash characters (~100,000 chars serialized). **The first draft of this paragraph got the characterisation wrong in the act of fixing a different figure**: it called the newline-every-5 stress input "what a real harvest entry or research ledger actually is", which is off by an order of magnitude — a real ledger measures 1.014x, not 1.21x. The number was reproducible; the sentence around it was not. That is the same defect as the similarity figure below, committed while correcting it, which is the argument for citing the input alongside every ratio rather than the ratio alone. **And the 2.01x ceiling is not a property of JSON escaping** — it holds because `server.ts` strips C0 control characters on every write path. A row of raw control characters, reachable only by calling `remember()` as a function rather than through the wire, serializes at **6.01x**; narrowing that sanitizer would silently triple this bound. The first draft of this entry and of the tool description both said "never more than the 50,000-char cap", which is a true statement about the row stated as though it were one about the response; the review caught it, and the bound test had to be rewritten too, because it asserted `size < rowChars * 1.2` and passed only because the fixture padded with characters JSON never escapes — pinning the fixture's escape density rather than the tool. It now bounds the envelope around `JSON.stringify(content).length`, with a companion case built from characters that all escape.
**It performs no write, and that is the load-bearing property.** `recall_count` and `last_recalled_at` are returned but never touched. The rule is not a new exception: `recall` is the only tool that calls `touchRecalledObservations`, while `context` and `export` — both targeted reads by entity name — have never bumped anything. Search bumps access telemetry; targeted reads do not; a fetch by id is a targeted read. **Stated honestly, the cost:** a row fetched repeatedly by id still reads as never-recalled to sleep-mode `prune`, which classifies "never recalled + old" as a delete candidate. That fails toward a visible false positive in a *proposal* the AI disposes of, not toward a deletion, and D11 already excludes append-only entities from `prune` entirely. The alternative — bumping — would mean a "let me check what this id is before I delete it" call permanently reshapes retrieval ranking, which is the exact side effect that made the `recall` path wrong.
**Failure shape:** an unknown id returns `success: false` with a message, not a throw and not an empty success. This is deliberately NOT the D13 hazard: there, an unparseable bound silently filtered everything out and an empty result was indistinguishable from an empty store. Here the caller named one specific id and is told that id was not found, which is a definite fact about a definite row. Mirrors `forget`'s not-found path. An observation whose entity row cannot be read gets its own message, which names BOTH possibilities and says the call cannot distinguish them — see the round-one findings below for why an earlier draft asserting "a data integrity problem, not a deleted memory" was wrong in the only situation that branch is reachable.
**Append-only entities get the content and a warning, not a withholding** — and the asymmetry with `near_matches` is deliberate. D20's preview cap withholds the *id* on those entities, because `remember` would otherwise be **offering** an unrequested destruction key beside a consolidation nudge; it previews the content on every entity and withholds only the id on append-only ones. `get_observation` is called with an id the caller already holds, which is the opposite shape; withholding content there would break reading a log entry, which is what logs are for. So the row comes back in full with `append_only: true` and an explicit "do NOT update, merge or otherwise consolidate". `append_only` is present and `false` on every other response, on the rule stated twice already in this log: a field that appears only in the dangerous case is indistinguishable from an older server that never had it (`replaced: false`, D10; `degraded: false`, D16).
**Not in `STRICT_TOOLS`, and the criterion says why rather than the omission being silent.** Strictness is justified by params whose silent loss WIDENS the operation. `get_observation`'s single param is what the tool acts on, not a restriction on a wider default: drop it and Zod's required check rejects the call, because absent the argument there is no operation to widen. Contrast `forget({entity})`, which stays a valid call meaning something far larger. The rationale is written into `param-normalization.ts` beside the two entries, so the next reader sees the test applied rather than a gap. It IS in `TOOL_PARAMS` — mandatory, since `tests/param-normalization.test.ts` pins that table against live `tools/list` output in both directions, and the drift guard was mutation-verified to fail without it.
**`onboard` was deliberately untouched while D20 was in flight, and the rewire shipped here once it landed.** Editing step 4 before that would have conflicted at merge on a decision that was not this one's to make. D20 landed mid-review, so the rewire is in this diff: step 1 now calls `get_observation({observation_id})` instead of `recall({query: "<the preview>", format: "full", limit: 5})`, and the boundary moves from "report-only above tens of thousands of characters" to the real constraint — **consolidate only when the combined text fits under `merge`'s 50,000-char cap**. `remember`'s own preview notice moves with it. The tool never depended on that rewire: its description carries the guidance, so it is discoverable from `tools/list` alone.
**Review round one caught a shipped falsehood, and it is the same mistake in a new place.** The tool description registered in `server.ts` — the one surface a model actually reads — advertised `near_matches[].observation_id` as an id source, in the present tense. At the time that description was written the field **did not exist here**: `near_matches` was `Array<{content, similarity}>` in `src/mcp/tools/remember.ts`, and the 200-char preview it also described applied only to append-only entities. Both came from branch `claude/zealous-bhaskara-725771`, which had not yet landed (it has now — see the landing note below, which is a separate point: the defect was asserting the field before it existed, not the field itself). Three surfaces in one diff told three different stories: this entry was honest about the branch, `CHANGELOG` omitted the field, and the tool description asserted it as fact — so a model would have called `remember`, gone looking for an id that was not there, and found the advertised workflow unusable, with nothing in the suite failing had that branch never landed. The fix was to describe only what this branch shipped and let the preview-cap branch add the rest when it landed, which is what happened; the alternative — asserting the field in a test so this branch cannot land first — was rejected because it makes an independent change hostage to a merge order nothing enforces. **The general shape: writing a description against a sibling branch's code is the same error as writing a report against data you have not fetched, and the honest surfaces elsewhere in the diff are what made it survive review-by-author.**
**The test that should have caught it was vacuous, in the way this repo has now been bitten five times.** It read `match.observation_id ?? first.observationId`, so the left side was always `undefined`, the id silently came from `remember` instead, and the test passed while exercising nothing it claimed to. Its name compounded the error: the fixture entity was not append-only, so no preview truncation happened either. It is replaced by three tests, one per id source that actually exists — `remember`, `recall` with `format: "full"`, `export` with `format: "json"` — each asserting the fetched content equals what that source reported, and each mutation-verified.
**Round one's other findings.** The boundary test hardcoded `const MERGE_CONTENT_CAP = 50_000` and never called `merge` or read its schema, so widening `.max(50000)` to `.max(500000)` left it green while this entry's load-bearing claim went false — it now reads `maxLength` off the live `tools/list` contract, and the mutation fails it. The telemetry-disclosure test compared `recall_count` without first asserting the fixture had been bumped, so it would have compared `0 === 0` if the query ever stopped matching. And the data-integrity branch asserted "this is a data integrity problem, not a deleted memory" in the one situation it is reachable — a second connection deleting the entity between this call's two un-transacted SELECTs — where the memory **had** been deleted, so the message stated the inverse of the truth; it now names both possibilities and says the call cannot distinguish them.
**Review round two confirmed every round-one fix and caught the correction introducing its own version of the defect it corrected.** Fixing an unmeasured similarity figure, this entry acquired an unmeasured *characterisation*: the newline-dense escaping ratio was real (1.20x) but was glossed as "what a real harvest entry or research ledger actually is", which is wrong by an order of magnitude — measured against this repo's own files, prose is 1.003x and a realistic log 1.014x. **A correct number with a wrong label is still a false claim, and the label is the part a reader acts on.** Round two also found this entry contradicting itself: the "Failure shape" paragraph still described the data-integrity message that the round-one fix had already removed, six paragraphs above the paragraph recording its removal — an append-only log needs the whole entry swept when a fix lands, not only the section about the fix. Two assertions were passing while the tool returned the wrong row entirely (neither checked that the returned `observation_id` was the one requested, and the boundary test's length control is satisfied by one row counted twice). The 2.01x ceiling turned out to be a property of `server.ts`'s C0 sanitizer rather than of JSON escaping, so it is now named as such. And a redundant `getEntityVersion` lookup was replaced by the `version_hash` already sitting on the `Entity` that `findEntityById` returns.
**The wire path is now tested, and the round-one blocker has a regression guard rather than only a fix.** Every other test calls `getObservation` directly, which skips registration, schema validation, param normalization and serialization — the exact gap the blocker lived in. Six tests now drive `tools/call` and `tools/list` through the full JSON-RPC shape the SDK's parsing wrapper requires. The important one is an **invariant, not a snapshot**: the description may advertise `near_matches` as an id source if and only if `remember` actually emits `observation_id` there. It held on this branch before the merge (no claim, no field) and holds after it (claim and field), failing only on the inconsistent state that shipped — so whoever landed the preview cap had to update the description in the same change. Nobody did, and the invariant is what said so.
**Two things checked at the merge gate, one of which was a real ambiguity.** (1) `onboard`'s new boundary first read "consolidate only when the combined text fits under 50,000", and "combined" is ambiguous between the sum of the sources and the merged text the model composes — only the second is the cap. Two heavily-overlapping 30,000-char siblings total 60,000 and may merge to 35,000, which is a perfectly good merge the first wording would have discouraged. It now says the cap is on the text you compose, gives both cases, and adds the rule that matters more than either: **never trim to fit**, because `merge` deletes the sources. (2) `remember`'s preview notice used to say the full text was "retrievable with recall", which needs no id; pointing it at `get_observation` makes it an instruction that needs one — and D20 withholds `observation_id` on append-only entities. That edit is safe, because the notice rides only the dedup-skip and replace paths and both are gated on `dedupEligible = !appendOnly && sameDay`, so an append-only write can never reach it. **That is a reachability argument, and this repo's rule is that a reachability argument gets tested, not reasoned** — two tests now pin it from both sides (the notice fires and every match it describes carries a resolvable id; the append-only message carries no id and prescribes no fetch), and both are mutation-verified.
**The merge-gate review found a data-loss path in the rewritten prompt, and it is D10's shape a third time.** On a `deduplicated: true` response the returned `observationId` is **not** what the caller just wrote — the write was skipped, and the id names a pre-existing, longer observation the caller has never seen. Step 4 asserted "the new observation is ALREADY stored by the time you read this", which is false there, and templated `merge([<this response's observationId>, <the near match's id>], content)`. A model composing that `content` from the text it submitted plus the fetched near match deletes whatever was unique to the stored row — silently, with `success: true` at every step. Verified on a probed fixture (0.864 similarity, stored row longer): the id returned is the prior row's, and it holds text the caller never sent. **The sentence and the template are D20's landed text, and the literal `novelty < 0.3` trigger cannot fire on a path that returns no `novelty` — but this diff is the first where the sequence reliably completes**, because step 1 now succeeds at any size and the new boundary licenses merging up to 50,000. The friction that used to stop it is gone, so the fix belongs here: step 1 now says re-read EVERY id you will pass to `merge`, names the `deduplicated: true` case explicitly, and the merge-not-update rule is scoped to responses that actually stored something. Pinned by a test whose control asserts the fixture reaches the dedup-skip branch at all, since a threshold drift would otherwise make it pass against a different code path.
**Renumbered twice, and the second one is the lesson.** `origin/main` advanced again *during* the final review and landed its own D21 (the `importance` ceiling), so this entry moved D21 → D22 → D23. The sweep was seven sites and had to be done **by line, not by file**: after the merge both `CLAUDE.md` and `DECISIONS.md` hold two D21 references, one of them main's, and a blanket replace would have rewritten a landed entry's own reference — the 2026-09-02 trap exactly, avoided only because it was anticipated. **The operational rule this session earned: `git fetch` immediately before push, not before merge.** A branch under review is a moving target, and this one moved twice, the second time twenty minutes after a fetch that showed nothing pending.

**Where:** `src/mcp/tools/get-observation.ts` (new), `src/mcp/server.ts` (registration), `src/mcp/param-normalization.ts` (`TOOL_PARAMS` entry + the `STRICT_TOOLS` exclusion rationale), `tests/get-observation.test.ts` (new), `src/mcp/tools/onboard.ts` (step 4 — step 1 re-points at `get_observation`, the boundary moves onto `merge`'s cap, and the `deduplicated: true` handle is named), `src/mcp/tools/remember.ts` (`PREVIEW_NOTICE`), plus the tool-surface enumerations in `README.md` and `PRODUCT.md` that a new tool has to appear in (both carried a hardcoded "11 tools"). ### D22 · 2026-09-09 · `recall`'s `similarity` is raw cosine on every path, and the similarity floor moves inside the search
**Why:** D21 disclosed two read-path defects and deliberately left them: `similarity` carried a raw cosine on the direct path and `sim * recallBoost * importance * SPREAD_DECAY` on the spread path — same key, same response, no marker — and `recall` sliced to `limit` inside a search that ranks by the boosted composite before filtering on raw similarity, so a boosted row could take a slot and then be dropped. Both are **pre-existing and reachable on `recallBoost` alone**, with `importance` untouched at its old ceiling: reproduced at a recall count of **100**, the exact figure `CLAUDE.md` uses as its own worked example of the boost (~1.46x). D21 amplifies neither into existence.
**The two defects are one shape seen twice, which is why they are one entry.** Both come from a score being used for one job and read as if it did another. The field carried the ranking composite where a caller expected a comparable measure; the slice was taken on the ranking composite where the caller's floor was a different measure. Fixing either without the other leaves the mechanism intact.
**What the field now means, stated once so it cannot drift.** `similarity` is the raw cosine between the query and that observation, on every path that computes one, and is **absent** where none was — a keyword-fallback row matched a `LIKE`, not a vector, and an absent similarity is the absence of one rather than a third meaning of the field. Ranking travels on an internal key stripped at a single exit, precisely as `semanticSearchWithVector` has always handled its own composite; that key is the search's score for direct rows, the same score damped by `SPREAD_DECAY` for spread rows, and a literal 0 for keyword rows. The registered tool description now says all of this, including the consequence a caller will otherwise read as a bug: **a row further down can carry a higher `similarity`, because the order is relevance and the number is not.** That was already true on `spread: false` before this change; it was simply never written down.
**The overflow above 1.0 was the available tell, and how reachable it is depends on which side of D21 you stand.** `recallBoost` is `1 + RECALL_BOOST_ALPHA·ln(1 + recall_count)` with no cap, so the spread composite can pass 1.0 — impossible for a cosine. At `importance = 1.0` that needs `sim · recallBoost > 2`, which for a near-verbatim match means a recall count above **22,025** (`e¹⁰ − 1`, where the boost reaches 2); the test fixture sits there, at cosine 1.0000 and a recall count of 100,000 → 1.076. **D21's landed ceiling of 2.0 changes that arithmetic materially**, and the first draft of this entry was written before it landed: at `importance = 2.0`, `importance · SPREAD_DECAY = 1.0` exactly, so the composite exceeds 1.0 whenever `sim · recallBoost > 1` — an ordinary similarity at an ordinary recall count. So the overflow is rare below D21 and unremarkable above it. Two corrections the review forced, both in this paragraph: the figure read "around 200,000", which is right only for `sim ≈ 0.90` and is contradicted by the same entry deriving the identical condition correctly as ~22,000 two paragraphs down; and the changelog's "exceeds 1.0 routinely" was an overstatement of the pre-D21 case. What actually happened in ordinary use was the quieter half of the same bug either way: every spread row under-reporting, at roughly half its true similarity. The guard pins the contract (`reported === cosineSimilarity(query, row)`) rather than either symptom, so it survives both regimes; the >1.0 arithmetic is asserted separately as the control proving the fixture can distinguish the two formulas at all.
**The floor moves into the search rather than the caller over-fetching.** `minSimilarity` on `SemanticSearchOptions` filters raw cosine **before** the sort-and-slice. Exact, where an over-fetch factor is a guess that fails silently at whatever multiple it did not anticipate — and free, because the function already loads and scores every row in memory before slicing, so the floor costs one comparison per row and no extra embedding work. `recall` keeps its own post-filter as a redundant guard, deliberately: "recall never returns a semantic row below the floor" should hold here whatever a future caller passes, rather than resting on an argument two modules away.

**Why:** the sole Dependabot critical (protobufjs RCE, GHSA-xq3m-2v4x-88gg, vulnerable `<=7.6.2`) enters *only* through the embedder chain `@xenova/transformers@2.17.2 → onnxruntime-web@1.14.0 → onnx-proto → protobufjs@6.11.x`. `npm audit fix --force` "resolves" it by downgrading `@xenova/transformers` to 2.0.1 — which breaks embedding generation, i.e. the whole recall layer. So instead a *scoped* override — `"overrides": { "onnx-proto": { "protobufjs": "7.6.5" } }` — pins protobufjs to a patched release only under onnx-proto, leaving the embedder at 2.17.2 untouched. In Node the native onnxruntime-node backend runs inference, so the pure-JS onnx-proto/protobufjs parse path is unreachable at runtime anyway; the override exists to clear the alert, and a separate reviewer proved it load-bearing (strip it → protobufjs falls back to 6.11.6 → the critical + 3 highs return). Everything else was in-range transitives cleared by a lockfile refresh + floor-bumps (`@modelcontextprotocol/sdk ^1.29`, `hono ^4.12.30`, `@hono/node-server ^1.19.14`, `tsx ^4.23.1` → esbuild 0.28.1). Verified: `npm audit` 14→0, 128/128 tests, embedder smoke (384-dim, cosine intact), `npm ci` clean on the VPS.
**Instead of:** (a) `npm audit fix --force` — rejected, downgrades transformers 2.17.2→2.0.1 and breaks the embedder; (b) migrating to `@huggingface/transformers` *now* — the correct strategic fix (removes onnxruntime-web@1.14/onnx-proto/protobufjs entirely, no override needed) but a larger change with existing-stored-vector-compatibility risk and a native-binding bump; deferred to its own verified ROADMAP item rather than rushed into a security patch. Note: npm does **not** persist `overrides` into `package-lock.json` — `npm ci` re-reads it from `package.json` and still pins 7.6.5 (don't be alarmed that `grep overrides package-lock.json` is empty).
**Status:** superseded by D5 (2026-07-17) — the deferred migration shipped; the override is removed. D4's interim-fix reasoning stands as the record of why the critical was patched (not migrated) inside the security remediation.

### D3 · 2026-07-17 · Bound MCP session lifetime with a server-side idle sweep (OOM fix)
**Why:** the `/mcp` handler kept one fully-wired `McpServer` per session in a Map that only evicted on an explicit client `DELETE` (the SDK transport's `onsessionclosed` fires nowhere else — verified in `webStandardStreamableHttp.js`). Claude.ai and most HTTP MCP clients reconnect with a fresh session and never DELETE, so sessions accumulated across ~7 weeks of uptime until the process OOM'd at ~1.9 GB *live* heap — while the DB was only 5.8 MB, which is exactly what made it look like a query/data problem and wasn't. Fix: `src/mcp/session-registry.ts` — per-session last-seen, a 30-min idle sweep evicts inactive sessions (unref'd timer), a 1000-session LRU backstop, and an in-flight guard so a busy session is never cut mid-request; `/health` now reports the live session count for verification.
**Instead of:** raising `--max-old-space-size` / adding a container `mem_limit` (rejected — a band-aid that only delays the same OOM as sessions keep accumulating; the leak is unbounded, so any ceiling is eventually hit); relying on clients to send DELETE (not in our control). Instrument-first (per-call logging + heap snapshot) was considered but the static + SDK evidence and the 7-week-uptime→OOM profile were conclusive, so the fix shipped directly.
**Status:** active.
**Where:** commit `17147ac` (`fix/mcp-session-leak` → main), deployed + verified 2026-07-17 (`/health` `sessions` gauge live, container `RestartCount=0`); failure-mode note in CLAUDE.md → Known Gotchas.
