# Hippocampus — Project Context

## What This Is
Open-source, self-hosted MCP memory server. Universal memory across Claude, ChatGPT, Gemini, Cursor, Perplexity — any AI platform that supports MCP.

"Your AI shouldn't forget who you are just because you switched apps."

## Stack
- Node.js 20+ / TypeScript
- Hono (web framework)
- `@modelcontextprotocol/sdk` (official MCP TypeScript SDK)
- Streamable HTTP transport on `/mcp`
- SQLite via `better-sqlite3-multiple-ciphers` (SQLCipher AES-256 encryption)
- `@huggingface/transformers` for local embeddings (all-MiniLM-L6-v2, q8 quantized)
- OAuth 2.1 with PKCE (self-contained, single user)
- Docker + Caddy reverse proxy

## Architecture
- Knowledge graph: entities → observations → relationships
- Semantic search via local embeddings (no external API keys)
- Entire database encrypted at rest (including embedding vectors — they leak original text)
- MCP tools: remember, recall, forget, update, merge, merge_entities, context, consolidate, export, check_version, onboard
- MCP resources: `hippocampus://context` (full knowledge graph, claude-md format), `hippocampus://entity/{name}` (per-entity context with relationships)

## Key Design Decisions
- **SQLCipher for everything**: Embeddings are NOT privacy-safe. Research shows text reconstruction from vectors. Encrypt the entire DB.
- **Local embeddings only**: No OpenAI/Anthropic API dependency. `all-MiniLM-L6-v2` runs in Node.js via Transformers.js.
- **OAuth 2.1 mandatory**: Claude.ai custom connectors need it. Self-contained auth server for single-user self-hosted.
- **Streamable HTTP**: Modern MCP transport. Not SSE (deprecated). Not stdio (local only).
- **No hosted version**: Open source, donations via Stripe Payment Link. No SaaS, no customer data liability.
- **Hono over Express**: Lighter, faster, works well with MCP middleware packages.
- **Consolidate = clustering only**: Hippocampus identifies duplicate clusters (embedding math). The AI does the merging (language intelligence). Each does what it's good at. The AI calls `merge` to finalize.
- **Dedup on write**: `remember` checks for near-duplicates (cosine similarity >= 0.85) on the same entity before storing. If existing content is longer/equal, skips. If new content is longer, **deletes the old observation** and replaces it. Conservative threshold — only catches near-verbatim repeats. Because that path is destructive, two guards bound it (D10): (1) **append-only entities** — those whose name matches a `HIPPO_APPEND_ONLY_PREFIXES` prefix (default `ops:daily-log:`, `ops:session-check`, `synthesis:`; unset **or blank** = defaults, since compose forwards unset vars as `""` and a blank must not silently unprotect anything — the literal `none` disables) are exempt from dedup entirely, neither skipped nor replaced; (2) **same-UTC-day scoping** — dedup only ever considers observations created on the same UTC calendar day, so two entries written on different days can never evict each other, however similar. A >= 0.85 match blocked by either guard is reported in `near_matches` rather than acted on. Calendar-day equality rather than a rolling window: a rolling window fails *destructively* at midnight (23:58 and 00:05 are 7 minutes apart and two different days' entries), day equality fails safe (worst case a duplicate is stored, which `consolidate` already handles).
- **Append-only entities are exempt from *invited* deletion too**: reporting overlap is the fix for the silent-eviction blindness, but `near_matches[].content` is byte-identical to the stored observation — the exact key `update` matches on — and `onboard` tells the AI that low novelty + high overlap means `update`/`merge`. So on append-only entities the reported content is truncated to a 200-char preview (non-executable by construction: a stray `update` fails safe with "no observation matching the old content") and the message says not to consolidate; `onboard` step 4 carries the matching exception. Full content is kept everywhere else, where consolidation is the intended workflow and needs the exact key. `consolidate` is covered too, as of D11 — see the next bullet.
- **`consolidate` excludes append-only entities from all four modes** (D11): it proposes and `merge`/`merge_entities`/`update` dispose, so on a log entity every proposal is a false positive by construction — two dated entries sharing a template are not duplicates, and a never-recalled old log entry is not dead weight, it is the record. Flagging was rejected as insufficient: a flagged cluster still ships full content + observation ids next to "use merge to consolidate", the same loaded-gun shape D10 removed from `remember`. Excluding also stops sleep-mode `prune` — which every `ops:daily-log:*` observation qualifies for, being old and never *individually* recalled — from burying the genuine candidates. `entities` mode is in scope because log entities share a namespace prefix by design: `ops:daily-log:codesea` vs `ops:daily-log:rsl-content` measures **0.688** against a 0.7 default, one threshold tweak from proposing a cross-project log merge. Every exclusion is counted in `excluded_append_only` and named in the message (never a silent drop, and never a bare "no observations found" on a log entity — that is the misleading all-clear again). `include_append_only: true` restores detection for the one real case: hunting accidental double-writes, which D10 made *more* likely by removing dedup from these entities.
- **Destruction is a top-level flag**: any `remember` result that deleted an observation carries `replaced: true` plus `replaced_observation` (full evicted text) and `replaced_observation_id`; `replace_kind` writes carry `replaced` + `replaced_count` + `replaced_observations` (every deleted id and its full text — unbounded by design: capping it would defeat the recoverability it exists for, so a `replace_kind` over many same-kind observations returns a large payload). Non-destructive outcomes carry `replaced: false`. Callers parsing a subset of fields can detect data loss without reading the `message` string.
- **A degraded search is a top-level flag, and an empty degraded search is an error**: `recall` used to swallow embedding failures (`semanticSearch(...).catch(() => [])`) and continue on keyword results alone — a smaller answer with `success: true` and nothing to distinguish it from a complete one, on the leg that is the *primary* search. Every response now carries `degraded: boolean` (`false` on the healthy path — absence must not be the all-clear, same reason as `replaced: false`) plus `degraded_reason` (error class + message, capped, never the query); the `compact`/`wire`/`index` formats also get a `DEGRADED` line inside `text`, since a caller reading `text` never sees a sibling field. When the semantic leg fails **and** the keyword fallback matches nothing, `recall` throws instead of returning `count: 0` — an empty result there is indistinguishable from an empty memory (D13's rule, same shape). `spread: true` still throws outright: without a query vector there is no dampened scoring, so keyword-only results are not a degraded spread but a different operation silently substituted for the requested one. `context`'s identical swallow was removed rather than flagged — its semantic leg is the last of exact → LIKE → semantic, so its degraded answer *is* the misleading one (`"No entity found"`). D16.
- **Merge = atomic consolidation**: Single tool call replaces multi-step `remember` + N x `forget` dance. AI provides merged text + observation IDs, Hippocampus handles the rest.
- **Storage guidance**: Tool descriptions encourage telegraphic form ("PhD atmospheric physics, TU Delft" not full sentences) to reduce per-observation token cost.
- **Compact recall format**: `format: "compact"` returns grouped markdown (~4x fewer tokens than full JSON). `format: "full"` (default) returns current shape for backward compat.
- **Budgeted context**: `hippocampus://context` resource capped at `HIPPO_CONTEXT_MAX_OBSERVATIONS` (default 100). Prioritizes most-recently-updated entities, partial-includes the last entity at the budget boundary.
- **Access tracking**: Schema V3 adds `recall_count` + `last_recalled_at` per observation. Foundation for decay-weighted retrieval. Updated on every recall match.
- **Entity resolution**: `consolidate mode: "entities"` embeds entity names, clusters by cosine similarity (default threshold 0.7). Detection only — AI decides what to merge. Surfaces cross-entity redundancy invisible to per-entity dedup.
- **Decay-weighted retrieval**: `score = similarity * (1 + 0.1 * log(1 + recall_count)) * importance`. Gentle boost from access tracking — similarity stays the dominant signal. recall_count=0 → neutral (no penalty), recall_count=100 → ~1.46x boost.
- **Observation importance**: Schema V4 — `importance REAL DEFAULT 1.0` per observation. Manual override for always-relevant facts. Set via `remember` tool's `importance` param (0.0-1.0). Multiplied into recall scoring.
- **Entity merge**: `merge_entities` tool — structural consolidation companion to `consolidate mode: "entities"`. Moves observations, embeddings, relationships atomically in a transaction, then deletes source entities.
- **Observation kind**: Schema V5 — optional `kind TEXT` per observation. Free-text, not enum — tool descriptions suggest `fact`, `decision`, `question`, `preference`. Filterable in both `recall` and `semanticSearch`. Included in JSON export. NULL for existing observations (backward compatible).
- **Spreading activation**: `recall` with `spread: true` — after base semantic+keyword search, follows relationships 1 hop from matched entities, scores related observations against the query, dampens by `SPREAD_DECAY = 0.5`, merges into results. Refactored `semanticSearch` into `semanticSearchWithVector` to avoid redundant embedding generation when spreading.
- **Contradiction detection**: `consolidate mode: "contradictions"` — finds observation pairs with high embedding similarity (same topic, default threshold 0.6) but low Jaccard word-set overlap (< 0.3). Surfaces conflicting claims for human review. No LLM needed — pure embedding math + lexical comparison.
- **Adaptive onboarding**: `hippocampus://context` resource counts total observations. If < 5, prepends guidance prompting the AI to capture user knowledge (identity, projects, preferences). Existing observations still shown below the guidance. At 5+, returns the full knowledge graph only. The old empty-state message ("No memories stored yet") is subsumed by the sparse branch.
- **Near-match detection on write**: `remember` already scans all entity embeddings for dedup (>= 0.85). Now also collects observations in the 0.5–0.85 similarity range — zero additional computation. Returns top 3 as `near_matches` in the response with a consolidation prompt. Encode-on-arrival: detect temporal redundancy at write time instead of waiting for batch `consolidate` passes.
- **Subspace novelty scoring**: `remember` returns `novelty` (0–1) via SVD projection. Pairwise cosine misses aggregate redundancy — five observations that individually have moderate similarity can collectively explain a new observation entirely. SVD projection compares against all observations simultaneously. When novelty < 0.1, the response flags it. Dependency: `ml-matrix` (~50KB, pure JS, zero native deps).
- **Sleep mode**: `consolidate mode: "sleep"` — batch lifecycle analysis inspired by hippocampal memory consolidation during sleep. SVD leverage scores + temporal signals classify observations into compress (redundant + old + recalled → merge candidates), prune (never recalled + old → delete candidates), and refresh (actively used + unique + old → reconsolidation candidates). Returns `information_rank` and `redundancy_ratio` per entity for structural diagnosis.
- **Reconsolidation hints**: `recall` flags `stale: true` on observations older than 30 days when the entity has received newer information since. Lightweight — date comparison only, no embedding computation. The AI can then use `update` to refresh stale facts. **Append-only entities are never flagged** (D12): the flag means "may need updating" and `update` is create-new + delete-old, so on a log entity it invites destroying a dated record — and it fired on *every* one of them, since "older than 30 days AND the entity has newer information since" describes every historical entry in an active log (measured on prod: 5 of 5 recalled log observations flagged stale). An old log entry is not out of date; it is the entry for that date.
- **Entity versioning**: Schema V6 — `version_hash TEXT` + `version_at TEXT` on entities. SHA-256 of all observation content sorted by observation ID, recomputed on every mutation via `updateEntityTimestamp`. Solves cross-platform staleness: an artifact stored via Claude is usable in Gemini/ChatGPT — the AI caches the hash and checks freshness later without re-fetching content.
- **Entity-level versioning, not observation-level supersession**: Original design considered `supersedes`/`superseded_by` on observations, but that requires soft-delete model — every query path (semantic search, keyword search, consolidate, export, context, spreading) would need supersession filters. Conflicts with `PRAGMA secure_delete = ON`. Entity version hash solves the actual problem (staleness detection) without touching the deletion model.
- **Version hash = SHA-256 of sorted observation content**: Sort by observation ID (UUID, stable), concatenate content with null byte separator, hash. Deterministic — same observations always produce same hash. Recomputed on every entity mutation via `updateEntityTimestamp` (already called by remember, update, merge, forget).
- **check_version tool**: Lightweight staleness check — AI sends entity name + cached `version_hash`, gets back `is_current` boolean + current version info. No embedding computation, no observation content returned. Purely metadata.
- **Version hash in tool responses**: All mutation tools (remember, update, merge, merge_entities) return `version_hash` so AIs can cache it. Recall includes `version_hash` per entity in all formats (full: per memory, compact/wire: entity header `[v:XXXXXXXX]`, index: appended to entity line). Context tool includes `version_hash` on the main entity.
- **Onboard tool**: Returns structured extraction instructions the AI follows to systematically capture user context. Lists existing entities to avoid duplicates. The tool doesn't extract anything itself — it returns a prompt. Keeps the tool stateless; each AI platform uses its own context for extraction. Optional `source` param adds platform-specific hint.
- **Adaptive onboarding updated**: `hippocampus://context` sparse guidance (< 5 observations) now mentions the `onboard` tool alongside direct `remember` usage.
- **Kind-scoped upsert (`replace_kind`)**: `remember` with `replace_kind: true` atomically deletes all existing observations with the same `kind` on the entity before inserting the new one. Designed for state observations that should have exactly one value (agent checkpoints, schedules). Skips dedup entirely — the caller explicitly wants replacement. Solves the `update` vs `remember` tradeoff for mutable state: `update` requires fragile exact-match on previous content; `remember` accumulates duplicates. `replace_kind` gives clean single-observation behavior without either failure mode.
- **Agent continuity layer**: Convention for storing agent instructions (scheduled tasks, workflows) in Hippocampus so any MCP-connected runtime can execute them. Entity type `agent`, observation kinds `instruction` (prompt), `schedule` (cron + requirements), `checkpoint` (last run state). No new tools, no schema changes — uses existing `remember`/`recall`/`context` with `replace_kind` for checkpoint writes. Spec: `docs/spec-agent-continuity.md`.
- **Sync script** (`scripts/sync-agents.ts`): Phase 1 tooling. Two commands: `push` migrates `~/.claude/scheduled-tasks/<id>/SKILL.md` → `agent:<id>` entities (uses `scripts/agents-manifest.json` to seed cron/requires since SKILL.md frontmatter doesn't carry them). `pull` materializes `agent:*` entities back to disk for Claude Code compat, backing up existing SKILL.md to `.bak`. Auth via `HIPPO_AGENT_TOKEN` env var; macOS Keychain fallback (`security find-generic-password -s hippocampus-agent -a karolina -w`). Run via `npm run sync-agents -- push|pull|list [--dry-run]`. Uses `replace_kind: true` on `remember` so re-running is idempotent. Uses a content-shape heuristic (`/^cron:/m && /^enabled:/m`) when distinguishing schedule from instruction observations, as a fallback for servers where `context` doesn't yet expose `kind`.
- **Context tool now exposes observation `kind`**: Schema V5 added `kind` per observation, but `context` tool's `formatObs` dropped it when serializing. Fixed — `context` response now includes `kind` alongside `content`, `source`, `remembered_at`. Unblocks any AI needing to differentiate observations by kind (e.g., agent sync separating `instruction` from `schedule`). Server-side change; requires redeploy to take effect.

## Security Rules
- NEVER log memory content, observation text, embeddings, tokens, or passphrase
- All endpoints behind rate limiting
- Input validation: 50,000 char max per memory, 200 char max entity name
- `PRAGMA secure_delete = ON` for forget operations
- Non-root Docker, cap_drop ALL, read-only filesystem (except /data)
- CORS restricted to known AI platform origins
- See SECURITY.md for full architecture

## Known Gotchas

- **npm `overrides` needs the `"$package"` reference form when the package is also a direct dependency — and editing `engines` after `npm install` leaves the lockfile stale.** `@hono/node-server` is both a direct dep and an override target (to force the MCP SDK's nested copy to the same major); a literal version in `overrides` that drifts from the dep spec throws `EOVERRIDE`, so use `"@hono/node-server": "$@hono/node-server"` (D8). Separately: any `package.json` edit made *after* the last `npm install` (e.g. bumping `engines.node`) isn't mirrored into `package-lock.json`'s root `packages[""]` entry until the next install — `npm ci` won't fail on it, but the next `npm install` dirties the lockfile in an unrelated commit. Rerun `npm install --package-lock-only` before committing. Also remember (from D4): npm never persists `overrides` into the lockfile at all — an empty `grep overrides package-lock.json` is normal.
- **An empty `near_matches` is not evidence that nothing was destroyed — it used to mean the opposite.** `remember`'s dedup scan put >= 0.85 matches into `bestMatch` (the destructive branch) and only 0.5–0.85 matches into `near_matches`, so at the exact moment a write DELETED an existing observation, `near_matches` came back empty — the most reassuring possible shape for the most destructive possible outcome. The eviction was announced only in the `message` string and `replaced_observation`, both of which callers reasonably drop when parsing a field subset, so the only reliable detector was an observation-count diff across the write, which nobody ran. Four confirmed losses on append-only entities before it was caught (2026-07-09 harvest entry; `ops:daily-log:nightly-check` 06-01; `synthesis:ingest-backlog` correction evicting the observation it was correcting, 2026-08-14; a 9,197-char harvest entry evicting the 6,182-char 07-31 entry on `ops:daily-log:hippocampus`, 2026-08-21 — three weeks apart, unrelated content, over the line purely on the shared harvest-log skeleton). Fixed 2026-08-21 (D10): the two guards above, plus blocked matches now surface in `near_matches` and every destructive result sets `replaced: true`. `consolidate` was the same hazard one tool over — it *proposes* what `merge`/`update` then delete — and is excluded as of D11. **General rule: when a write path can delete, check what its "all clear" signal is actually measuring** — and if a caller cares about durability, diff the observation count. **Second-order shape, caught in review of the fix itself:** making the overlap visible re-created the same loss one layer up — the response quoted the full prior entries back (byte-identical to the stored content, i.e. a valid `update` key) under the message "consider consolidating", while `onboard` instructs the AI to consolidate exactly that pattern. The server stopped deleting and started *asking the model to*, on every daily-log write, and it would have looked like the fix working. Hence previews-not-content on append-only entities. When you replace a destructive behaviour with a report, check what the report authorises.
- **A date bound compared against a stored timestamp is a STRING comparison, and `T` sorts above the space.** `created_at` is TEXT holding SQLite `datetime('now')` output (`YYYY-MM-DD HH:MM:SS`, space-separated, UTC), so `created_at >= ?` orders lexicographically. ASCII `T` is 0x54 — above the space (0x20) and above every digit — so `recall({since: "2026-08-25T00:00:00"})` compared greater than every row in the table and returned **0 results with `success: true` and no error**, while the space-separated form of the same instant returned 37. The broken spelling was the one the tool's own schema documented ("Only return memories after this ISO date"). Fixed 2026-08-26 (D13) by `normalizeSinceBound` in `src/db/timestamps.ts` — call it on any caller-supplied date before it reaches SQL. The two DB search functions (`searchObservations`, `semanticSearchWithVector`) take a pre-normalized bound and, as of D15, **assert** it — `assertStoredSinceBound` throws if the bound is not the stored form and a real instant, so a second caller that forwards a raw date fails loudly instead of matching nothing. D13 had left that contract to a jsdoc, and a characterization test pinning "raw `T` returns zero rows here" would have blessed the reintroduction. **Two general rules fall out.** (1) The failure direction is what hid it: a filter that silently returns *nothing* is indistinguishable from "nothing was stored", which is why the only thing that caught it was a negative control against a boundary already known to hold data — when a query returns zero, test a bound you KNOW has rows before believing the zero. (2) Never `new Date()` a stored timestamp: a zone-less string is parsed as **local** time (ES2015+ — only date-only forms are UTC, and the `T` separator does not change this), so every age computation silently depends on the host's offset. The container is UTC and a Helsinki laptop is +3, from the same database. Use `parseStoredTimestamp` from the same module.
- **`context()` blows up on append-only log entities.** Entities like `ops:daily-log:*`, `ops:knowledge-patterns`, or `pipeline:qualification-patterns` accumulate many observations over time. `context(topic: "...")` can return 100K+ chars and exceed token limits — the harness saves the response to a file with offset/limit instructions, but that breaks your flow. For log-style entities, use `recall(query, format: "index" | "compact")` first to see what's there, or open the saved file with offset/limit. Long-term fix: a token budget on `context` similar to `HIPPO_CONTEXT_MAX_OBSERVATIONS` for the resource.
- **An MCP tool failure is IN-BAND, so a client that only catches exceptions counts it as a success.** A rejected `tools/call` comes back as HTTP 200 with a normal `content` array and `isError: true` beside it — there is no throw and no non-2xx status. `scripts/sync-agents.ts`'s `call()` read `content[0].text`, tried `JSON.parse`, failed (the text is `Error: …`), and returned the raw string; `cmdPush` counts `ok++` whenever `call` does not throw, so a `remember` the server REJECTED printed `✓`, reported `Pushed 5/5 agents` and exited 0 having written nothing. On the read side the same gap gave `pull` a string where it expected an object (`undefined.matchAll`, cause discarded) and turned a failed `context` into the false message `no 'instruction' observation, skipping`. Exact sibling of the `claude -p --output-format json` trap in the global notes: **any MCP client must check `isError` explicitly — the transport succeeding is not the tool succeeding.** Fixed 2026-09-02 (D17); `call()` throws on the flag, and the script gained a main-module gate so this stays regression-testable.
- **VPS lives at `/opt/hippocampus` on Hetzner** (NOT `~/hippocampus`). SSH config alias is `hippo`. Deploy = `git push origin main` then `ssh hippo 'cd /opt/hippocampus && git pull && docker compose up -d --build'`. Container runs read-only filesystem; `/data` is the only writable volume. No `docker-compose.override.yml` — single compose file. Healthcheck takes ~15s after restart.
- **On the hippo box, `git pull` reporting "Already up to date" does NOT mean your commit is what got built.** Concurrent worktree sessions are the normal setup here, and they deploy the same box. A sibling that pulled first leaves the box legitimately up to date with *its* commit, so your deploy rebuilds at a HEAD you never pushed — the pull is truthful and the build is green, and nothing in the output names the commit. Hit 2026-09-02: `git pull` said up-to-date, the box was at `2830ca1` (a sibling's merge), and current `origin/main` was two commits further on. The D14 code happened to be an ancestor, so the right thing shipped by luck. **Always print the box's HEAD after the pull and compare it to the commit you intended** (`ssh hippo 'cd /opt/hippocampus && git log --oneline -1'`), and re-check `git log --oneline main..origin/main` on the box — a stale local `origin/main` ref there can make a genuinely-behind checkout look current until an explicit `git fetch`. Then verify behaviorally, per the entry above. Sibling rule from the merge side: when main advanced under you, **run the full suite against the merged state before trusting a green deploy** — 271/271 is what made that merge safe to ship, not the clean auto-merge.
- **Zod tool schemas STRIP unknown args — they don't reject them.** An unrecognized key in a tool call vanishes before the handler runs, and on a tool whose scope depends on which args are present, that silently *widens* the operation: `forget({entity, content})` became `forget({entity})` and deleted the whole entity (2026-07-27, `skill:pseo-llm-visibility`). Any future tool where present-vs-absent args change the blast radius must go into `STRICT_TOOLS` in `src/mcp/param-normalization.ts` (unknown args throw, naming the key only — never the value). "Let Zod reject it" is not a real fallback; Zod won't. **The criterion is scope, not destructiveness** (D14): `recall` is read-only and is strict too, because it carries restricting params — `recall({query, from: "..."})` drops the bound and answers with the whole history under `success: true`, which a scheduled "what's new since my last run" sweep reads as entirely new. The key-side mirror of D13's value-side bug, failing toward presence instead of absence. **The thing that makes strictness safe is the drift guard, not the `STRICT_TOOLS` entry**: `TOOL_PARAMS` is a hand-maintained copy of every tool's params with nothing linking it to the registered schemas, so adding a param to a strict tool and forgetting it there turns a valid documented call into a hard error — `tests/param-normalization.test.ts` pins `TOOL_PARAMS` against the live `tools/list` output both directions across all tools, and pins every semantic alias to a real param (the alias branch runs *before* the strict check, so a stale alias fails silently). Add the param in both places, or the guard fails first. **Own-property checks are load-bearing here**: `TOOL_PARAMS`/`SEMANTIC_ALIASES` are plain object literals, so `k in aliases` was true for `constructor`/`toString`/`__proto__` — those keys took the alias branch and skipped the strict throw altogether, and a tool *named* `constructor` resolved to the `Object` function and crashed on `canonical.has is not a function`. Fixing that with `Object.hasOwn` then exposes `__proto__` to a bare `out[k] = v`, which writes the prototype instead of a key. Use `Object.hasOwn` for every lookup and `Object.defineProperty` for every assignment in that module.
- **MCP client tool param names ≠ entity field names.** `context` expects `topic`, not `entity`. Easy to get wrong when refactoring — load the schema via ToolSearch when in doubt rather than guessing from existing tool-call patterns. Mitigated since 2026-05-22: `src/mcp/param-normalization.ts` accepts `entity`/`entity_name`/`entityName` as aliases for `topic` on `context`, and `entity_name`/`entityName` for `entity` on `forget`, plus generic snake↔camel conversion across all params. Canonical names are still the wire contract — only inbound leniency is added.
- **Don't wrap tool `inputSchema` with `z.preprocess()` or `z.object().transform()` to mutate args before validation.** The SDK's `tools/list` runs `normalizeObjectSchema` on each tool's input — that helper only unwraps raw shapes and ZodObjects (it checks `.shape` directly). A `ZodEffects` (which is what `z.preprocess` and `.transform` return) returns `undefined` from `normalizeObjectSchema`, so `tools/list` falls back to `EMPTY_OBJECT_JSON_SCHEMA` and AI clients silently lose all param signatures. To run pre-validation logic, install at the request-handler boundary instead — see `installParamNormalization` in `src/mcp/server.ts`.
- **`_requestHandlers.get('tools/call')` returns a schema-parsing wrapper, not the raw McpServer dispatch.** The SDK's `Protocol.setRequestHandler` wraps user handlers with `parseWithCompat(CallToolRequestSchema, request)`, so anything reaching back into `_requestHandlers` (including our own normalization wrapper) must accept and pass through the full JSON-RPC shape `{ jsonrpc, id, method, params }`. Tests that drive the handler directly need to construct that full shape — see `tests/param-normalization.test.ts` for the pattern.
- **Typecheck-before-commit is a *git* hook, not a Claude Code `settings.json` hook.** `.claude/settings.json` once carried a `"PreCommit"` hook running `npm run typecheck` — but `PreCommit` is not a Claude Code hook event (those fire on the Claude Code lifecycle: `PreToolUse`, etc., never on `git commit`), and the shape was wrong too, so `/doctor` flagged it and it silently never ran. The real enforcement lives in tracked `.githooks/pre-commit`, activated per clone with `git config core.hooksPath .githooks` (a non-zero hook exit aborts the commit — standard git). Deliberately no husky/postinstall: running `git config` during the Docker `npm ci` build fails (no `.git` present) and breaks the image. Fixed 2026-06-08 (`29d71dc`).
- **Before treating a "deploy X" roadmap item as undone, check whether X is already live.** "Deploy" TODO items go stale: the `context` kind fix (`c46ea72`, committed 2026-04-15) sat as an unchecked deploy item for ~2 months while already running on prod — an unrelated later redeploy had picked it up. Verify *behaviorally*, not via SSH or commit hash: call the live tool through the `claude.ai Hippocampus` connector (→ `hippo.sarna.rocks/mcp`) and inspect the actual response (e.g. does `context` return observation `kind`?). A needless redeploy just restarts the container — and stales any running MCP sessions.
- **MCP sessions leak one `McpServer` each without a server-side idle sweep → eventual OOM.** The Streamable HTTP transport only drops a session on an explicit client `DELETE` (`onsessionclosed` fires nowhere else). Claude.ai and most clients reconnect with a fresh session and never DELETE, so the `/mcp` session map in `src/index.ts` grew one retained `McpServer` per session across ~7 weeks of uptime until the process OOM'd at ~1.9 GB *live* heap — while the DB was only 5.8 MB. The small DB is why it looked like a query/data bug and wasn't; the crash's `better-sqlite3 .all()` stack frame was just the allocation that tipped an already-full heap. Fixed 2026-07-17 (`17147ac`, D3) with `src/mcp/session-registry.ts`: 30-min idle sweep + LRU cap + in-flight guard. **Diagnostic:** `/health` now reports live `sessions` — if it climbs monotonically and never falls, the sweep has regressed. Recognise the failure by `FATAL ERROR: Reached heap limit` in `docker logs` that is unrelated to DB size, plus a slowly-climbing `RestartCount` over weeks.
- **Request-level diagnostics live in Caddy's journal, not `docker logs`.** The container logs only startup lines ("OAuth 2.1 enabled", "Hippocampus starting…") — there is no per-request logging in the app. To see what a failing client is actually sending/getting (status codes, `Mcp-Session-Id`, auth presence), use `ssh hippo 'journalctl -u caddy --since "20 minutes ago" | grep /mcp'` — Caddy logs full request/response metadata per hit (Authorization is redacted). This is how the 2026-07-28 stale-session 400 was caught: docker logs showed nothing while the journal showed Claude's `tools/call` getting 400 with a stale session id.
- **Requests with an evicted/unknown `Mcp-Session-Id` must get HTTP 404, never 400.** The sweep above made eviction routine, which exposed this: the `/mcp` route's fallthrough handed stale-session requests to a fresh uninitialized transport, which answered `400 "Bad Request: Server not initialized"` — and MCP clients treat 400 as fatal, so every Claude session idle >30 min (or orphaned by a container restart) had a permanently dead Hippocampus connection. Per the Streamable HTTP spec, 404 is the signal that makes clients transparently re-initialize; verified live 2026-07-28 (a broken Claude Code session recovered on its next tool call). Fixed `b8cd5cf`; body shape mirrors the SDK's own session-not-found response (`-32001`, `id: null`). Repro/verify: POST `/mcp` with a valid bearer token and a bogus `Mcp-Session-Id` → expect 404.
- **Tests import `{ app }` from `src/index.ts` — startup only runs behind the main-module gate, and every module-level `setInterval` must be `.unref()`'d.** Since `1ceb9d0`, `initDatabase()`/signal handlers/`serve()`/embedding backfill sit inside an `isMain` block (`import.meta.url` vs `pathToFileURL(process.argv[1])`); node:test files drive routes via `app.request()` after setting env + calling `initDatabase()` themselves (pattern: `tests/mcp-session.test.ts`). A module-level timer without `.unref()` keeps each node:test worker alive indefinitely — the suite *hangs*, it doesn't fail (this is exactly how `rate-limit.ts`'s cleanup sweep bit). Any new periodic timer follows the existing unref'd trio: session sweep (index.ts), OAuth cleanup (oauth.ts), rate-limit cleanup.
- **The `isMain` gate copied from `src/index.ts` reads FALSE behind a symlinked path, and what that costs depends on what it guards.** Node resolves symlinks for `import.meta.url` but NOT for `process.argv[1]`, so `import.meta.url === pathToFileURL(process.argv[1]).href` is false whenever the file is reached through a symlink — reproduced via macOS `/tmp` → `/private/tmp`: `npx tsx /tmp/<symlink>/scripts/sync-agents.ts pull` printed **nothing and exited 0**, while the same file by its real path ran normally. For `src/index.ts` this is nearly harmless (nothing starts listening; you notice in seconds) and it still carries the original form. For a CLI it is indistinguishable from "nothing to do" — so `scripts/sync-agents.ts` deliberately diverges and compares `realpathSync()` on **both** sides (in a try/catch, since `realpathSync` throws on a missing path). **Any new entrypoint that gates on `isMain` should use the realpath form**, and note the trigger is real here: a symlinked `~/GitHub`, an external volume, or a CI scratch dir under `/tmp`.
- **To test an embedding failure, poison the model load — don't try to stub the module.** ESM bindings can't be monkeypatched and `mock.module` is unreliable under `tsx`, but the real failure mode is reproducible offline and deterministically: before importing anything from `src/`, `import { env } from '@huggingface/transformers'` and set `env.allowRemoteModels = false`, `env.localModelPath = '<nonexistent>'`, plus `process.env.TRANSFORMERS_CACHE` to the same path. The first `generateEmbedding` then rejects with a genuine transformers model-load error. Two consequences: the pipeline is a **module-level singleton cached on first success**, so one poisoned file cannot also hold a healthy-path case (put those in a different file — node's test runner gives each file its own process); and fixtures must be seeded through the DB layer (`findOrCreateEntity`/`createObservation`), never `remember`, which needs a working embedder. Always assert `generateEmbedding` rejects *first* — every other assertion in such a file also passes against a working embedder. Pattern: `tests/recall-degraded.test.ts`.
- **An unquoted heredoc EXECUTES backticks in the body — including ones inside comments and string literals of the embedded language.** `python3 - <<PY … PY` (unquoted delimiter) makes bash expand `$var`, `$(…)` and `` `…` `` across the whole body *before* python3 ever sees it. So a copy-paste remediation hint written as `` `ssh hippo 'reboot'` `` inside a Python comment is not documentation — it is a command, and bash runs it. That exact line rebooted the production hippo box mid-session on 2026-08-07 (`~/chief-of-staff/fetch-hippo-metrics.sh`); a sibling backtick also fired `ssh hippo 'apt update && apt upgrade'` (which installed nothing only because `apt upgrade` aborted at its no-TTY confirm prompt). Symptom shape: a burst of `foo: command not found` errors naming fragments of your own prose, followed by a Python `SyntaxError` whose source line contains the *output* of some command. **Fix: always quote the delimiter (`<<'PY'`) and pass paths in via the environment** (`JSON_OUT="$JSON_OUT" python3 - <<'PY'` … `os.environ["JSON_OUT"]`). Interpolating shell variables into an embedded script is the whole trap — the convenience is one `$VAR`, the cost is arbitrary execution of anything you later write in prose.
- **docker-compose's `${VAR:-}` idiom forwards an UNSET variable as an empty string, and zod `.optional()` does not skip `""`.** Compose cannot express "absent", so every var in the `environment:` allowlist arrives as at least `""`. Two consequences, both live. (a) Any config default keyed on `undefined` never fires for a forwarded-but-unset var — `HIPPO_APPEND_ONLY_PREFIXES` was drafted as "empty = no exemptions", which would have silently disabled the D10/D11/D12 data-loss protection on prod the moment the var was merely wired through the compose file. Hence blank-means-defaults with a literal `none` sentinel to disable; **any new guard-ish env var must fail safe on `""`, not on `undefined`.** (b) `z.string().min(32).optional()` and `z.string().url().optional()` REJECT `""` (optional only skips `undefined`), so `HIPPO_AGENT_TOKEN`/`HIPPO_OAUTH_ISSUER` forwarded-but-unset make `loadConfig()` throw at boot — a fresh self-hoster who sets neither cannot start the container. Karolina's prod sets them, which is why it never surfaced. Spawned as its own task 2026-08-21.
- **Writing two similar observations to the same non-append-only entity in a test silently collapses them into one.** Dedup-on-write replaces at >= 0.85 when the new content is longer, so a fixture pair intended as "two observations" becomes one and every downstream assertion (cluster count, prune list length) quietly measures the wrong thing. Bit the D11 control tests. Fix: backdate the first observation (`UPDATE observations SET created_at = datetime('now','-21 days')`) so the same-UTC-day guard keeps both — which is also more realistic, since the real entries were written weeks apart. **Corollary for any test asserting something is now suppressed: assert the fixture WOULD have fired first.** A `remember`-dedup fixture measured 0.703 against the 0.85 threshold and a `consolidate` contradictions fixture never cleared the pairing predicate at all — both "passed" while proving nothing, and both were caught only by an explicit precondition assert (`assertWouldHaveDeduped`) or a CONTROL call with the guard disabled. Similarity thresholds are not guessable; probe the pair with `generateEmbedding` + `cosineSimilarity` before writing the test around it.
- **`git fetch origin main:main` refuses while the main worktree has `main` checked out, so in a feature worktree local `main` silently goes stale.** Concurrent worktrees are the normal setup here, and after pushing with `git push origin HEAD:main` the local `main` ref stays pinned at whatever it was — so `git diff main...HEAD` over-reports, folding already-merged commits into what looks like the current diff. A code reviewer handed the wrong range will review merged work as if it were new. **Use `origin/main` for every range comparison in a worktree** (`git diff origin/main...HEAD`, `git log origin/main..HEAD`), and `git fetch origin` first.
- **`docker system prune -af` on the hippo box is box-wide and briefly bounces the container.** It removes unused images/networks across *every* project on the VPS, not just hippocampus cruft — a 2026-07-17 cleanup reclaimed 26 GB (disk 49%→15%) but also swept a dormant `tended` project's images and an old unused `caddy:2-alpine` image (harmless — they rebuild on next start). **Never pass `--volumes`** — the encrypted `/data` DB lives in a volume and must be preserved (the default prune leaves volumes alone). It momentarily recreates the running hippocampus container (Node process uptime resets; `RestartCount` stays **0** — a clean recreate as the prune clears the old container's layer, not a crash), and the daemon may emit a one-off `rw layer snapshot not found for container <id>` mid-sweep — benign, that id is the old container being removed. **Caddy is a host systemd service** (`systemctl is-active caddy`), not a container, so the public HTTPS proxy is insulated from Docker prunes. For a zero-blip cleanup use `docker builder prune -f` (build cache only — where the bulk accumulates from repeated `compose up --build`; leaves containers/images untouched).
- **Verify a deploy with one `curl` against the PUBLIC endpoint, never an ssh polling loop.** After `docker compose up -d --build`, the obvious move is to poll `/health` over ssh until it comes up. Don't: a `for` loop with `sleep` + `ssh` blew the 5-minute tool timeout and then failed every subsequent connection with `ssh_dispatch_run_fatal: … Can't assign requested address` — rapid repeat connections exhaust local ephemeral sockets, and the failure looks exactly like the box being down when it is in fact fine. **Caddy is a host systemd service, so the public endpoint stays up across a container recreate**: `curl -s https://hippo.sarna.rocks/health` answers in one shot with `status`, `version`, `uptime`, `db`, `memory_mb` and `sessions`, no ssh at all. Use ssh only for what the endpoint cannot tell you (`docker inspect -f "StartedAt={{.State.StartedAt}} RestartCount={{.RestartCount}}"`, or grepping the compiled bundle in the running container to prove the new code actually shipped — `docker exec hippocampus grep -c "<newSymbol>" /app/dist/<path>.js`, which is the behavioural check the "is X already live" gotcha above asks for).
- **`/health`'s `uptime` is process seconds, and a resumed session makes it look like a phantom restart.** Reading `uptime: 1010` right after a deploy and `uptime: 609364` "later" in the same conversation reads as a 7-day jump on a process started 25 minutes ago — an alarming shape that invites hunting a crash loop that never happened. The gap was real elapsed time: the session had been resumed a week later. **Check the current date against the deploy timestamp before treating any monotonic counter as anomalous** — `docker inspect -f "{{.State.StartedAt}}"` plus `date -u` settles it in one call, and `RestartCount` is the field that actually distinguishes a restart from a long quiet uptime. Related but distinct from the OOM entry above: there the signal is `sessions` climbing monotonically and never falling, which one reading can never establish.
- **Your loaded MCP tool schema can be a stale cache, so never conclude a `.describe()` change failed to ship from the schema you hold.** After deploying the D13/D15 `since` work, the `recall` schema in this session still read *"Only return memories after this ISO date"* — the pre-D13 wording — which looks exactly like the tightened description having been lost in a merge. It had not: both `src/mcp/server.ts` and the compiled bundle inside the running container carried *"Only return memories at or after this UTC time"*. The client had cached `tools/list` from before the restart (same family as the known post-restart session staleness). **Check the source and `docker exec … grep` the running container before reporting a shipped-wrong tool description**; the schema in front of you is the least authoritative of the three.
